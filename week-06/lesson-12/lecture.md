## Зачем миграции в микросервисе

База живёт дольше кода. Через полгода у вас есть прод, стейджинг и три
дева; схема «создана руками по заметкам» — это гарантия того, что стейдж
расходится с продом, а онбординг нового разработчика занимает неделю.
Миграции решают три задачи:

1. **Схема = код.** Версия схемы привязана к версии сервиса, обзор в PR,
   история в git.
2. **Воспроизводимость.** Любая среда поднимается одной командой: новая
   машина, CI, тестовый контейнер.
3. **Эволюция без драм.** Каждое изменение схемы — отдельный файл с
   `up` (применить) и `down` (откатить), применяется по порядку версий.

В монолите миграции — удобство. В микросервисе с контрактом «каждый
сервис владеет своей базой» — единственный честный способ: **схема
принадлежит сервису**, как и его код. Никакой общей базы, никаких
ручных ALTER в продакшене.

## goose: версионные миграции

[pressly/goose](https://github.com/pressly/goose) — де-факто стандарт
миграций в Go (SQL-first; альтернатива — golang-migrate, подход тот же).

Файл миграции — обычный SQL с аннотациями:

```sql
-- +goose Up
CREATE TABLE orders (
    id          text PRIMARY KEY,
    customer_id text NOT NULL,
    status      text NOT NULL,
    total       bigint NOT NULL,
    created_at  timestamptz NOT NULL
);

-- +goose Down
DROP TABLE orders;
```

Имя файла несёт версию: `0001_create_orders.sql` — goose применяет файлы
по порядку номеров и ведёт таблицу `goose_db_version` (какая версия уже
применена). `goose up` применяет всё до последней, `goose down` откатывает
на одну, `goose status` показывает состояние.

Правила, которые стоят за простым форматом:

- **Миграция атомарна.** PostgreSQL DDL транзакционен, но не всё
  (CREATE INDEX CONCURRENTLY — нет); по умолчанию goose оборачивает
  каждую миграцию в транзакцию, для нетранзакционных вещей есть
  `-- +goose NO TRANSACTION`.
- **Один логический шаг = одна миграция.** Не «одна миграция на неделю
  работы»: каждое изменение схемы — отдельный файл. 0002 с таблицей
  outbox — пример правильного размера.
- **Down пишется честно.** Откат должен возвращать схему в прошлое
  состояние. Миграция без down — мина: раскатка вперёд пройдёт, откат
  релиза — нет.
- **Никакого ручного ALTER после миграции.** Всё, что попало в БД руками,
  расходится с тем, что миграции создают с нуля.

## embed: миграции внутри исполняемого файла

В Go файлы можно вшить в исполняемый файл на этапе компиляции:

```go
package migrations

import "embed"

//go:embed *.sql
var FS embed.FS
```

`//go:embed` — директива компилятора: при сборке SQL-файлы попадают в
исполняемый файл. Дальше goose работает прямо с `fs.FS`:

```go
goose.SetBaseFS(migrations.FS)
goose.SetDialect("postgres")
if err := goose.Up(db, "."); err != nil { ... }
```

Почему это важно: сервис разворачивается **одним исполняемым файлом** (урок 1) — отдельные
каталоги с SQL пришлось бы задачать отдельно в Docker-образ, а при
`CGO_ENABLED=0` и scratch-образах это целая история. Embed закрывает
вопрос целиком: миграции — часть артефакта, применить их может сам сервис
на старте (`goose.Up` в `main`, до начала обработки запросов) — или
отдельная команда/джоба.

Аналог в Python: Alembic читает `versions/` с диска, и их нужно класть в
образ отдельно (плюс сам Alembic и его зависимости); в Go нет среды выполнения,
который читает файлы, — поэтому компилятор вшивает их сам.

## testcontainers: реальная БД в тестах

Юнит-тесты на sqlmock (урок 11) не проверяют главного: что SQL-запросы
синтаксически верны и типы совпадают. testcontainers-go поднимает
настоящий PostgreSQL в Docker прямо из теста:

```go
container, err := postgres.Run(ctx,
    "postgres:16-alpine",
    postgres.WithDatabase("orders"),
    postgres.WithUsername("orders"),
    postgres.WithPassword("orders"),
    testcontainers.WithWaitStrategy(
        wait.ForLog("database system is ready to accept connections").
            WithOccurrence(2).WithStartupTimeout(60*time.Second)),
)
if err != nil {
    t.Skipf("Docker недоступен — пропускаю: %v", err)
}
dsn, _ := container.ConnectionString(ctx, "sslmode=disable")
```

Ключевые моменты:

- **Версия БД зафиксирована**: `postgres:16-alpine` — тесты гоняются на
  той же мажорной версии, что прод. Обновили прод — обновили строку в
  тесте.
- **Готовность ≠ запущен контейнер.** Процесс postgres стартует дольше,
  чем открывается порт; без wait-стратегии первые запросы получат
  `connection refused` — флаки. `wait.ForLog(...)` ждёт, пока база реально
  готова принимать.
- **Один контейнер на suite, не на тест.** Поднять PostgreSQL — секунды,
  но пять раз по секундам на 10 тестах — это уже минуты. Suite
  (`SetupSuite`/`TearDownSuite`) поднимает БД один раз, тесты внутри
  работают с одной базой.
- **`t.Skip` при недоступном Docker** — честный пропуск с причиной.
  На dev-машине без Docker тесты не должны валиться, но в CI Docker
  обязан быть: иначе «зелёные тесты» ничего не проверяют (skip виден в
  отчёте, за этим следят).

## Интеграционные тесты: testify suite

```go
type IntegrationSuite struct {
    suite.Suite
    container *postgres.PostgresContainer
    db        *sql.DB
    repo      *repository.PostgresOrderRepository
}

func TestIntegration(t *testing.T) { suite.Run(t, new(IntegrationSuite)) }

func (s *IntegrationSuite) SetupSuite() {
    // контейнер → dsn → sql.Open("pgx", dsn) → goose.Up → repo
}
```

Структура повторяет `main`: та же последовательность «контейнер → пул →
миграции → репозиторий». Интеграционные тесты проверяют сценарии, которые
sqlmock принципиально не ловит:

- **Roundtrip**: `Save` → `GetByID` вернул то же (включая точность
  `timestamptz` — PostgreSQL хранит микросекунды, `time.Time` — нано:
  сравнение требует `Truncate(time.Microsecond)`, иначе флак).
- **`sql.ErrNoRows` → доменная ошибка** на реальном «нет строки».
- **`UpdateStatus` + чтение** — реальные UPDATE.
- **Фильтры `List`** — реальный WHERE на реальных строках.

Тесты в одном suite разделяют базу — **идентификаторы данных должны
быть уникальны между тестами** (иначе PK-конфликты; в практике — префиксы
`rt-`, `upd-`, `list-`).

Обратная сторона: интеграционные тесты медленные (секунды на старт
контейнера) — их держат отдельно от юнит-тестов или хотя бы помнят, что
`go test ./...` теперь не мгновенный.

## Go vs Python: Alembic, pytest-docker

```python
# Alembic: версии на Python, применяются alembic upgrade head
def upgrade() -> None:
    op.create_table(
        "orders",
        sa.Column("id", sa.Text(), primary_key=True),
        ...
    )
```

Alembic — тот же принцип версионных миграций, но на SQLAlchemy:
`upgrade()`/`downgrade()` на Python с автогенерацией diff'а схемы
(`alembic revision --autogenerate`). goose — чистый SQL, diff схемы
пишется руками (для 5 таблиц это не потеря).

Тесты: в Python связка pytest + pytest-docker/pytest-postgresql поднимает
БД для сессии; Go-эквивалент — testcontainers (есть и Python-версия той
же библиотеки, testcontainers-python). Существенная разница: Python-стек
несёт с собой SQLAlchemy-движок и драйверы в среде выполнения, Go-стек —
статический исполняемый файл с вшитыми миграциями и драйвером pgx.

**C#**: EF Core Migrations — миграции на C# (модель → diff → SQL),
применяются приложением на старте; близко к связке «goose + embed».

## Подводные камни и анти-паттерны

1. **Один контейнер на каждый тест.** Минуты вместо секунд. Один на
   suite; данные тестов — уникальные id.
2. **Skip, который никто не видит.** `t.Skip` на недоступном Docker —
   норма для локальной разработки, но в CI интеграционные тесты обязаны
   исполняться. Проверяйте отчёты на skip.
3. **Сравнение времени без Truncate.** `time.Time` с наносекундами против
   `timestamptz` с микросекундами — «Equal» не сойдётся. Обрезайте до
   микросекунд.
4. **Миграции руками в проде.** Всё, что сделано ALTER'ом вручную,
   отсутствует в миграциях — следующая среда не воспроизведётся.
5. **`-- +goose NO TRANSACTION` забыт** для CONCURRENT-индексов — миграция
   падает или зависает.
6. **Порядок применения ≠ алфавит.** Номера версий — 0001, 0002...
   (goose требует ровно числовой префикс). Отдельный `goose_db_version`
   не редактируйте руками.
7. **Тест ждёт готовности БД сном.** `time.Sleep(5s)` — флак под
   нагрузкой. Только wait-стратегия (`ForLog`).
8. **NULL-колонки без смысла.** В `outbox.published_at` NULL — состояние
   «не опубликовано», его нельзя заменять датой по умолчанию: это
   семантическая ошибка, которую заметит неделя 8.
9. **Секреты в DSN в коде.** Пароли тестовых контейнеров — только для
   тестов; прод-секреты — через env/secret-менеджер.
10. **Миграции без down.** Откатить релиз нельзя; в проде начнётся
    ручная починка схемы.
