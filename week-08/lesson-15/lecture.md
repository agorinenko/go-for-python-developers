# Урок 15. Kafka: событийная шина

## Цели урока

- понять, зачем микросервисам события и когда они **не** нужны;
- разобрать модель Kafka: топики, партиции, ключи, оффсеты, consumer groups, rebalance;
- осознать, что значит at-least-once по умолчанию — и как это меняет код;
- настроить продюсера на kafka-go и спроектировать сериализацию с учётом эволюции схем;
- опубликовать первое событие итогового проекта — `OrderCreated`.

## Задача из итогового проекта

Сервис `orders` до сих пор общался с миром синхронно: HTTP/gRPC, PostgreSQL.
По контракту [CAPSTONE.md](../../CAPSTONE.md), неделя 8, он начинает
**публиковать события**: топик `orders.created`, ключ партиционирования —
`order_id`, payload — `{"order_id", "customer_id", "items", "total",
"created_at"}`. На этом уроке — продюсер и сериализация; на следующем —
transactional outbox, который сделает публикацию надёжной.

## Зачем события в микросервисах

Синхронный вызов `orders → payments.create()` связывает сервисы средой выполнения:
payments должен быть жив, быстр и иметь ту же SLO. Разомкнутая схема — «orders
опубликовал факт, кому надо — тот подписался» — даёт три выигрыша:

1. **Развязка по времени и доступности.** Если payments лежит — событие ждёт
   в брокере. Продюсер не получает таймауты из-за чужого развёртывания.
2. **Масштабирование подписчиков.** Один топик читают N независимых групп
   консьюмеров: платежи, аналитика, email — продюсер о них не знает.
3. **Аналитика и аудит.** Шина — это журнал фактов предметной области.
   Прошлые события можно перечитать: восстановить состояние, отладить,
   пересчитать отчёты.

Цена — **отложенная согласованность**: заказ создан, а платежи об этом ещё не
знают. Система обязана быть корректной при любом порядке и любом числе
повторов событий. Если ваша бизнес-логика требует «создал заказ → тут же
получил ответ платежей» — это синхронный RPC, а не событие.

## Модель Kafka за 10 минут

**Топик** — именованный журнал. Физически разбит на **партиции** — упорядоченные
неизменяемые последовательности записей, реплицированные по брокерам. Каждая
запись имеет номер — **оффсет**, уникальный в пределах партиции.

Продюсер выбирает партицию: явно, по **ключу** (стабильный hash — все записи
одного ключа идут в одну партицию, порядок в рамках ключа гарантирован) или
round-robin. Запись **не переписывается и не удаляется по значению** — живёт до
retention (время/размер). Это журнал, а не очередь в памяти: прочитанное не
исчезает.

**Consumer group** — группа консьюмеров, которые делят партиции топика:
каждая партиция доставляется ровно одному члену группы в каждый момент.
Другие группы читают тот же топик независимо со своих оффсетов.

**Rebalance** — перераспределение партиций между членами группы при изменении
её состава. Во время rebalance консьюмер получает паузу: отписался → сброс
заявленных партиций → новый план → снова читает. Важные следствия: обработка
должна быть **идемпотентной** (сообщение после rebalance придёт ещё раз),
`max.poll.interval.ms` обязан быть больше времени обработки батча (иначе
«живой» консьюмер будет вечно выкидываться из группы), а повторные попытки внутри
обработки должны быть ограничены таймаутом.

## Гарантии доставки: at-least-once по умолчанию

Kafka по умолчанию — **at-least-once**:

- продюсер переотправляет, если не получил ack в срок (ack мог потеряться
  **после** записи — дубликат);
- консьюмер коммитит оффсет асинхронно/батчем; крах между обработкой и
  коммитом — повторная доставка;
- rebalance — повторная доставка.

Что это значит для кода: **консьюмер обязан быть идемпотентным**. Один
`OrderCreated` может прийти дважды — обработка дважды не должна изменить
результат (дедупликация по `order_id` — тема следующего урока).

Про «exactly-once»: внутри Kafka возможен idempotent producer + транзакции
(один топик/партиция), но **сквозного** exactly-once «Kafka + ваша БД» не
существует без транзакционного протокола с внешним хранилищем. Практически
все промышленные системы строятся на at-least-once + идемпотентность: это
проще, быстрее и не хрупко.

## Продюсер: batch, async, ошибки

Продюсер не пишет в сеть на каждый `send` — он буферизует. Настройки, которые
определяют компромисс «латентность против пропускной способности»:

- `BatchSize` (байт) и `BatchTimeout` — когда батч уходит;
- `Async: true` — не ждать ответа на каждое сообщение; ошибки приходят через
  канал `writer.Completion` (или молча теряются, если канал никто не читает!);
- `RequiredAcks` — `RequireNone` (fire-and-forget), `RequireOne` (лидер),
  `RequireAll` (все реплики — медленно, но долговечно);
- retry — в kafka-go `MaxAttempts` (по умолчанию 10) + backoff.

Ошибки бывают **retryable** (сеть, «not leader for partition» — переизбрание
лидера — клиент переподключится к новому лидеру сам) и не-retryable
(`MessageTooLarge`, неизвестный топик). Различать их нужно, чтобы не крутить
повторная попытка до посинения: в kafka-go есть `kafka.Temporary(err)` для временных
ошибок.

## Сериализация: JSON против protobuf, эволюция схем

Событие — это **контракт навсегда**: аналитика может читать прошлогодние
записи. Два пути:

**JSON** (наш выбор для `orders.created`): человекочитаемость, отладка,
совместимость с не-Go подписчиками. Правила эволюции: добавлять поля —
безопасно (старые консьюмеры игнорируют неизвестное), переименовывать/удалять/
менять тип — только через версионирование (поле `schema_version` или топик
`orders.created.v2`).

Событие в практике — это **отдельная структура**, а не `json.Marshal(Order)`:

```go
type orderCreatedEvent struct {
    OrderID    string        `json:"order_id"`
    CustomerID string        `json:"customer_id"`
    Items      []orderItemEvent `json:"items"`
    Total      int64         `json:"total"`      // копейки, всегда int
    CreatedAt  time.Time     `json:"created_at"` // RFC 3339
}
```

Так внутренняя модель может меняться свободно, а контракт шины — нет.

**protobuf** — компактнее в разы и со схемой в Confluent Schema Registry
(эволюция проверяется при публикации). Цена: инфраструктура, кодогенерация,
бинарный формат в отладке. Для высокочастотных событий (клики, телеметрия) —
обоснованно; для десятков событий заказа в секунду — преждевременно.

Золотое правило: **схема события — отдельный замороженный артефакт** (в
итоговом проекте зафиксирована в CAPSTONE.md), а не «что удобно продюсеру сейчас».

Ключ сериализуем отдельно от значения: ключ — примитив (`order_id`), партиция
вычисляется по **сырому** байтовому ключу — менять его представление нельзя,
иначе разъедется распределение по партициям.

## kafka-go (segmentio): ключевые настройки

kafka-go — чистая Go-реализация без cgo (в отличие от confluent-kafka-go,
обёртки над librdkafka). Продюсер — `kafka.Writer`:

```go
writer := &kafka.Writer{
    Addr:     kafka.TCP("kafka:9092"),
    Balancer: &kafka.Hash{},     // партиция по ключу — стабильный порядок на ключ
    RequiredAcks: kafka.RequireOne,
    BatchTimeout: 10 * time.Millisecond,
    MaxAttempts: 5,
}
defer writer.Close()

err := writer.WriteMessages(ctx, kafka.Message{
    Topic: "orders.created",
    Key:   []byte(orderID),
    Value: payloadJSON,
})
```

Советы по настройке:

- `Balancer: &kafka.Hash{}` — обязателен, если порядок в рамках ключа важен;
- `Async: true` — только когда поняли, кто читает `Completion`, и что ошибки
  там не теряются;
- `WriteTimeout` на Writer и `context.WithTimeout` на каждый вызов — иначе
  неотвечающий брокер повесит горутину надолго;
- `Writer.Close()` — флашит буфер; без него в асинхронном режиме хвост
  сообщений теряется;
- Writer потокобезопасен — один на сервис, а не на запрос.

Полный цикл публикации с обработкой ошибок и таймаутом:

```go
func publishOrderCreated(ctx context.Context, w *kafka.Writer, orderID string, payload []byte) error {
    ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()

    err := w.WriteMessages(ctx, kafka.Message{
        Topic: "orders.created",
        Key:   []byte(orderID),
        Value: payload,
    })
    switch {
    case err == nil:
        return nil
    case kafka.Temporary(err):          // сеть/лидер недоступен — retryable
        return fmt.Errorf("publish %s (temporary): %w", orderID, err)
    default:                            // MessageTooLarge и т. п. — не лечится повторной попыткой
        return fmt.Errorf("publish %s (fatal): %w", orderID, err)
    }
}
```

Консьюмер — `kafka.Reader` с `GroupID` (тогда работают rebalance и
`CommitMessages`). Для саги payments на следующем уроке понадобятся
`GroupID`, `FetchBatchMin/Max`, `CommitInterval`:

```go
reader := kafka.NewReader(kafka.ReaderConfig{
    Brokers:   []string{"kafka:9092"},
    Topic:     "orders.created",
    GroupID:   "payments",
    MinBytes:  1,
    MaxBytes:  10e6,
    MaxWait:   500 * time.Millisecond,
})
for {
    msg, err := reader.FetchMessage(ctx) // читаем...
    if err := handle(msg); err == nil {
        _ = reader.CommitMessages(ctx, msg) // ...и коммитим ТОЛЬКО успешно обработанное
    }
}
```

Коммит только после успешной обработки + идемпотентный `handle` — это и есть
корректная at-least-once связка.

## Проектирование топика `orders.created`

Партиции задаются при создании топика и **не уменьшаются** — увеличение
числа партиций не сохраняет порядок в рамках ключа для старых сообщений.
Запас «на вырост» при создании (скажем, 6–12 партиций для сервиса заказов)
дешевле, чем миграция на другой топик. Retention — по бизнес-требованиям:
события нужны аналитике через месяц или год — retention задаёт горизонт
«перечитываемости» журнала. Компакшн для `orders.created` не нужен (это
журнал фактов, а не таблица «текущее состояние»).

## Go vs Python

Python-мир знает два варианта:

```python
# confluent-kafka: обёртка над librdkafka (C)
producer = Producer({"bootstrap.servers": "kafka:9092"})
producer.produce("orders.created", key=order_id, value=json.dumps(payload),
                 callback=lambda err, msg: log.error(err))  # async!
producer.flush()  # иначе хвост теряется при выходе
```

```python
# aiokafka: нативная asyncio-реализация
async with AIOKafkaProducer(bootstrap_servers="kafka:9092",
                            key_serializer=str.encode) as producer:
    await producer.send_and_wait("orders.created", key=order_id, value=payload)
```

Различия, которые важно перенести:

- **Ошибки.** confluent-kafka по умолчанию асинхронен: ошибка приходит в
  callback — легко забыть `flush()`/callback и молча потерять события.
  В Go `WriteMessages` по умолчанию синхронен: ошибка — возвращаемое
  значение, и «забыть» её заставляет только явное игнорирование.
- **Celery как «события через брокер»**: `task.delay(...)` поверх RabbitMQ —
  это события через брокер, но с другим контрактом: Celery подразумевает
  «выполни функцию», Kafka — «зафиксируй факт». Celery-задачи не перечитываются
  через месяц, у них нет retention-журнала и независимых групп подписчиков.
  Если вы привыкли «отправить в очередь — оно выполнится», в Kafka вы
  отправляете **факт**, а подписчик сам решает, что делать.
- **Консьюмеры**: в Python параллелизм консьюмера — это процессы/пулы
  (`concurrency=prefetch` в Celery, потоки/задачи в aiokafka); в Go — одна
  горутина на партицию внутри процесса, и масштабирование группы — просто
  больше реплик приложения.

## Подводные камни и анти-паттерны

1. **«Опубликовал — значит произошло».** После `WriteMessages` без повторной попытки при неудачном подтверждении
   и без обработки ошибки событие может быть потеряно. Публикация — сетевой
   ввод-вывод с теми же правами на ошибку, что и запись в БД.
2. **Ключ = всё подряд.** Ключ `user_id` при топике заказов — ок; ключ
   `created_at` — почти наверняка hot partition (все пишут в одну партицию в
   момент времени). Слишком мало ключей → skew, слишком много уникальных →
   бессмысленный hash.
3. **Изменение ключа/сериализации задним числом.** Старые сообщения в топике
   переедут не в те партиции и перестанут читаться. Схема и ключ — контракт.
4. **Долгая обработка в консьюмере** без учёта `max.poll.interval.ms` —
   бесконечные rebalance, группа «живёт» на 2 партициях из 20.
5. **Синхронная публикация в критическом пути без таймаута** — брокер стал
   точкой отказа сервиса заказов. Лечится таймаутом + outbox (следующий урок).
6. **`Async: true` без чтения `Completion`** — молчаливая потеря ошибок;
   канал `Completion` не буферизован, горутина писателя блокируется, пока его
   никто не читает.
7. **Payload — внутренняя структура Go.** `json.Marshal(order)` с
   неэкспортированными деталями утекает в контракт. Сериализуйте **событие** —
   отдельную структуру с замороженными именами полей, как в практике.
8. **Ретраи без backoff** — шторм повторных попыток в момент недоступности
   брокера; kafka-go по умолчанию делает backoff, не отключайте его без нужды.

## Что делаем в итоговом проекте

1. Создаём `internal/events`: тип `Event`, интерфейс `Transport`,
   `Publisher.PublishOrderCreated` — сериализация по контракту недели 8,
   uuid v4 через `crypto/rand` (без внешней зависимости — 16 байт, биты
   версии/варианта), ключ — `order_id`.
2. `kafkatransport` — реализация `Transport` поверх `kafka.Writer`
   (`Balancer: &kafka.Hash{}`).
3. Подключаем публикацию в `CreateOrder` после успешного сохранения;
   `main.go` создаёт Writer и Publisher.
4. Помним: это временная схема — на уроке 16 публикация переедет в
   transactional outbox, а `Transport` и сериализацию переиспользует реле.
