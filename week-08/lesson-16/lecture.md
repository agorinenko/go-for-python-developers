# Урок 16. Transactional outbox и saga

## Цели урока

- понять проблему двойной записи «БД + брокер» и почему «опубликовал после COMMIT» теряет события;
- освоить паттерн transactional outbox: таблица + фоновое реле, at-least-once поверх него;
- спроектировать идемпотентных консьюмеров (дедупликация) и saga — choreography против orchestration;
- разобрать DLQ и повторные попытки; понять, когда outbox избыточен.

## Задача из итогового проекта

На уроке 15 сервис публиковал `OrderCreated` «в лоб» после сохранения заказа.
Теперь по контракту CAPSTONE.md (неделя 8) публикация идёт **только через
outbox**: событие пишется в таблицу `outbox` в одной транзакции с заказом
(схема заморожена на неделе 6: `event_id uuid`, `event_type text`,
`payload jsonb`, `published_at NULL` = не опубликовано), фоновое реле
публикует и помечает `published_at`, а консьюмер-сага `payments`
обрабатывает события идемпотентно с дедупликацией по `order_id`.

## Проблема двойной записи

Создание заказа — это **две записи в разные системы**, между которыми нет
общей транзакции:

```go
tx, _ := db.Begin(ctx)
tx.Save(order)          // 1. БД
tx.Commit()             // 2. COMMIT
err := kafka.Send(orderCreated)  // 3. брокер
```

Что может пойти не так:

- краш после COMMIT до `Send` — событие **потеряно навсегда** (аналитика
  и payments его никогда не увидят, БД и шина разошлись);
- краш после `Send` до обработки ответа — неясно, записалось ли;
- `Send` в самой транзакции (до COMMIT) — наоборот: событие ушло, а
  COMMIT откатился (например, нарушение ограничения) — событие о заказе,
  которого нет.

Это и есть проблема **dual write**: без распределённой транзакции нельзя
атомарно записать в БД и в брокер. «Опубликую после COMMIT» не решает её,
а лишь делает потерю редкой — редкие потери ровно поэтому самые дорогие.

## Паттерн transactional outbox

Брокер из цепочки убирается — остаётся **одна** транзакция:

```
BEGIN;
  INSERT INTO orders ...;
  INSERT INTO outbox (event_id, event_type, payload) VALUES (...);
COMMIT;
```

Запись в `outbox` — обычный INSERT в той же БД, он COMMIT-ится или
откатывается **вместе** с заказом. Согласованность «заказ ↔ событие»
теперь гарантирует ваша СУБД, а не сеть.

В коде сервиса это выглядит так:

```go
func (s *OrderService) CreateOrder(ctx context.Context, ...) (*domain.Order, error) {
    tx, err := s.db.Begin(ctx)
    defer tx.Rollback(ctx) // no-op после Commit

    order, err := tx.SaveOrder(ctx, ...)
    if err != nil { return nil, err }

    event := events.OrderCreatedEvent{OrderID: order.ID /* ... */}
    payload, _ := json.Marshal(event)
    if err := tx.InsertOutbox(ctx, order.ID, events.TypeOrderCreated, payload); err != nil {
        return nil, err
    }
    if err := tx.Commit(ctx); err != nil { return nil, err }
    return order, nil // событие уже «в пути» — в таблице, не в воздухе
}
```

**Реле** — фоновый процесс:

1. `SELECT ... FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT 100`;
2. публикует каждое сообщение в брокер;
3. `UPDATE outbox SET published_at = now() WHERE id = ANY(...)`.

Ключевое свойство реле: **порядок по id** (порядок транзакций) и
**частичный прогресс** — при сбое на 3-м сообщении первые два помечаются,
недоставленные остаются `published_at IS NULL` и уйдут в следующем цикле.
Это и есть at-least-once: между публикацией и UPDATE снова может быть крах —
событие уйдёт дважды. Поэтому outbox не заменяет идемпотентность, а
переносит её на сторону консьюмера.

Скелет цикла реле (полная версия — в практике):

```go
func (r *Relay) Run(ctx context.Context) {
    t := time.NewTicker(r.interval)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            if n, err := r.ProcessOnce(ctx); err != nil {
                logger.Error("outbox relay cycle failed", "published", n, "err", err)
            }
        }
    }
}
```

`ProcessOnce` — сердце: fetch батчем по возрастанию id → send по одному →
`MarkPublished` для успешно отправленных **всегда**, даже при ошибке на
следующем сообщении (частичный прогресс).

Гарантии реле честно ограничены:

- **хотя бы один раз** — да (повторная публикация возможна);
- **порядок** — в пределах одного id (и в пределах одной партиции, если ключ
  стабилен), но не глобально;
- **ровно один раз** — нет и не будет: дубликаты неизбежны, дедупликация —
  задача консьюмера.

Вариации: polling по таймеру (наш случай — просто и предсказуемо),
`LISTEN/NOTIFY` в PostgreSQL (низкая латентность), Debezium/CDC (реле вообще
не пишется — события читаются из WAL). Для учебного итогового проекта и большинства
реальных сервисов polling c интервалом 0.5–5 с достаточно.

## Идемпотентные консьюмеры: дедупликация

At-least-once значит: **консьюмер обязан пережить повтор**. Правило простое —
эффект двукратной обработки равен эффекту однократной. Инструменты:

1. **Идемпотентность операции.** «Списать 100₽» — не идемпотентно;
   «установить статус paid» — идемпотентно. Переписывайте логику на
   «установи состояние», а не «примени действие».
2. **Дедупликация по ключу** (`Seen` из практики): `event_id`/`order_id` +
   таблица обработанных ключей с уникальным индексом —
   `INSERT ... ON CONFLICT DO NOTHING` атомарно решает гонку «две реплики
   обрабатывают одно событие»:

   ```sql
   INSERT INTO processed_events (order_id) VALUES ($1)
   ON CONFLICT (order_id) DO NOTHING;
   -- вернул 0 строк — событие уже обрабатывали, пропускаем
   ```

   Ключ в таблицу кладётся **в той же транзакции**, что и эффект обработки:
   только тогда «увидел ключ» означает «эффект точно есть».
3. **Естественная идемпотентность.** `UPDATE ... WHERE status='new'` — второй
   прогон не найдёт строку и ничего не сделает.

Дедупликация в памяти (наша практика) — для одного процесса; в итоговом проекте
payments хранит обработанные `order_id` в БД — сага может перезапускаться.

## Saga: распределённая транзакция без 2PC

Сага — последовательность локальных транзакций, каждая публикует событие
или команду для следующего шага, с **компенсациями** на случай отказа:
заказ создан → оплата → (успех) резерв склада / (отказ) заказ в `cancelled`
и событие `OrderCancelled`.

Два стиля:

- **Choreography** (наш выбор): сервисы общаются напрямую через события,
  оркестратора нет. Просто, нет единой точки отказа, но логика «размазана»
  по событиям — её не видно из кода одного места.
- **Orchestration**: выделенный сага-сервис шлёт команды и хранит состояние
  машины. Логика в одном месте, но появляется «бог-объект» и лишний хоп.

Правило компенсаций: компенсация должна быть **идемпотентной** и
**непроваливаемой** (если отказ оплаты не смог отменить заказ — сага
застревает; такие хвосты лечат DLQ и ручной разбор).

## DLQ и повторные попытки

Сообщение, которое не удаётся обработать (битый payload, зависимость лежит),
нельзя терять и нельзя ронять консьюмер бесконечно:

1. **Ретраи с backoff** — только для временных сбоев (сеть, дедлок);
   число попыток конечно.
2. **Dead Letter Queue** — после N попыток сообщение уходит в
   `orders.created.dlq` (в kafka-go: отдельный Writer при исчерпании
   попыток), а основной поток продолжает жить.
3. **Алерт на DLQ** — DLQ без мониторинга хуже, чем падение: сообщения
   тихо гниют. Разбор DLQ — штатная процедура: причина, фикс, реплей.

Ограничение порядка: повторная попытка одного сообщения задерживает следующие в
партиции — либо обрабатывайте с параллелизмом внутри партиции (меняя
порядок — только если бизнес позволяет), либо выносите повторные попытки в отдельный
топик.

## Когда outbox избыточен

Outbox — это цена за консистентность. Он не нужен, если:

- событие не «производное от транзакции», а самодостаточное (лог, метрика,
  «пользователь кликнул» — потеря одного события допустима);
- согласованность обеспечена иначе (идемпотентный консьюмер
  восстанавливает состояние из самого события или из БД);
- событий нет вовсе — синхронный RPC честнее (см. урок 15).

Диагноз простой: **«если мы потеряем это событие, данные разойдутся
навсегда?»** Если да — outbox. Если расхождение лечится реконсиляцией или
несущественно — не усложняйте.

## Go vs Python

**Python, Celery + django-transaction:**

```python
from django.db import transaction
from django.db.transaction import on_commit
from myapp.tasks import publish_order_created

@transaction.atomic
def create_order(payload):
    order = Order.objects.create(**payload)
    # on_commit: задача уйдёт в брокер ТОЛЬКО после COMMIT —
    # аналог outbox «на минималках», но события хранятся в памяти процесса
    transaction.on_commit(lambda: publish_order_created.delay(order.id))
    return order
```

`on_commit` закрывает «публикацию до COMMIT», но **не** закрывает «краш
после COMMIT до отправки»: колбэки живут в памяти процесса, событие ещё не
записано никуда долговечного. Полноценный outbox в Python — либо таблица +
периодическая задача, либо библиотеки уровня `django-outbox-pattern`,
`transactional-outbox` (Dramatiq/Postgres). Celery-задачи сами по себе —
это «выполни функцию», а не журнал фактов: реплея через месяц нет.

В Go разница не в языке, а в том, что реле — это 50 строк с `context` и
`time.Ticker` (наша практика), без фреймворков: интерфейсы `Store` и
`Transport` очерчивают границы, тесты подменяют оба.

## Подводные камни и анти-паттерны

1. **`SELECT` без `ORDER BY id` + без `LIMIT`** в реле — недетерминированный
   порядок и неконтролируемый батч; id и есть порядок транзакций.
2. **Mark всех при сбое одного.** «Отправил 3 из 5 — пометил все 5» = потеря
   двух событий. Частичный прогресс обязателен.
3. **Ошибка mark = повторная отправка всего батча.** События уже доставлены,
   но `published_at` не проставлен — дубликаты обеспечены. Это нормально
   (at-least-once), лишь бы консьюмер дедуплицировал.
4. **Дедупликация «в памяти после обработки».** Обработал → положил в map →
   краш → повтор. Класть ключ в БД нужно **в той же транзакции**, что и
   эффект обработки.
5. **Ретрай навсегда внутри обработчика.** Партиция встала, группа ребалансит,
   соседние события не обрабатываются. Конечные попытки + DLQ.
6. **Outbox на каждый чих.** Логи и метрики через outbox — лишние записи,
   лишнее реле, лишняя латентность. Outbox — для событий, которые меняют
   состояние других систем.
7. **Таймауты реле больше интервала.** Следующий цикл стартует, пока прошлый
   ещё публикует — два реле «гоняются» за одним батчем. Либо таймаут <
   интервала, либо guard от перекрытия циклов.
8. **Компенсация, которая сама падает.** Сага застревает навсегда. Компенсации
   должны быть простыми и идемпотентными; их сбои — в DLQ с алертом.

## Что делаем в итоговом проекте

1. `internal/events`: реле outbox (`Relay`: `Run` + `ProcessOnce` с частичным
   прогрессом) поверх `Store` — реализации на pgx по таблице `outbox` из
   миграции недели 6.
2. `CreateOrder`: запись заказа **и** события в `outbox` в одной транзакции;
   прямая публикация урока 15 удаляется.
3. Сага `payments`: консьюмер топика `orders.created` с дедупликацией по
   `order_id` (таблица обработанных ключей, `ON CONFLICT DO NOTHING`);
   неудачная оплата → статус `cancelled` + компенсирующее событие.
4. Неуспешные после N попыток сообщения — в DLQ с алертом.
