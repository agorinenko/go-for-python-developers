# Урок 17. Память и аллокации

## Цели урока

- разобрать внутреннее устройство slice и string: заголовок, подлежащий массив, рост;
- понять, откуда берутся аллокации и как их видеть (`-gcflags="-m"`, `testing.AllocsPerRun`);
- освоить инструменты дешёвой работы с памятью: `strings.Builder`, `strconv.Append*`, предварительная ёмкость, `sync.Pool`;
- научиться осознанно выбирать между value и pointer в структурах и аргументах;
- узнать минимум о GC, необходимый для эксплуатации: GOGC, STW, триколор.

## Задача из капстоуна

Сервис заказов вышел в строй, и горячий путь — валидация позиций и
сериализация DTO — крутится на каждый запрос. Неделя 9 в капстоуне:

поэтому урок начинается с устройства памяти в Go.

## Внутренности slice и string

Слайс — это **заголовок из трёх машинных слов**: указатель на подлежащий
массив, длина, ёмкость. Присваивание слайса копирует заголовок, а не данные:

```go
a := []int{1, 2, 3}
b := a[:2]       // тот же массив, len=2
b[0] = 99        // a[0] тоже 99 — aliasing!
```

Строка — заголовок из **двух** слов (указатель + длина) над неизменяемым
массивом байтов. Отсюда два практических следствия:

1. Передача слайса/строки в функцию дешёва — копируется заголовок, не данные.
2. Конверсия `[]byte ↔ string` в общем случае **копирует** данные (строки
   неизменяемы — иначе бы нарушилась их immutability). Каждая такая конверсия
   в цикле — лишняя аллокация и memcpy. Исключение — оптимизации компилятора
   для частных случаев (`map[string]` lookup по `string([]byte)`).

## Рост слайсов

`append` пишет в запас ёмкости; когда его нет — выделяет новый массив и
копирует. Стратегия роста: до 256 элементов — удвоение (раньше и далее),
после — мягче, примерно ×1.25. Следствия:

- рост амортизированно дешёв, но **каждая точка роста — аллокация + копия**;
- `make([]T, 0, n)` с честной оценкой ёмкости убирает весь рост: для 1000
  элементов это 10+ аллокаций против 1;
- `append(a, b...)` может переиспользовать массив `a` — источник тех самых
  «призрачных» мутаций, когда `a` ещё кому-то нужен.

## strings.Builder против конкатенации

`+` для строк — новый массив и копия всего накопленного на каждый шаг:
квадратичная сложность по длине результата (в Python это скрыто оптимизациями
CPython для refcount==1, в Go — честная копия).

```go
// Плохо: O(n²) и аллокация на каждую итерацию
var s string
for _, p := range parts { s += ", " + p }

// Хорошо: strings.Builder — один растущий буфер, 1–2 аллокации
var b strings.Builder
b.Grow(estimated)
for i, p := range parts {
    if i > 0 { b.WriteString(", ") }
    b.WriteString(p)
}
s := b.String()  // единственная финальная копия (или ноль — см. ниже)
```

Детали, которые важно знать: `b.String()` копирует буфер (мутации после не
должны менять строку); `b.Bytes()` отдаёт буфер **без копии** — можно
отдавать наружу, только если Builder больше не трогается; `Grow` с честной
оценкой убирает рост буфера. Числа форматируйте без аллокаций:

```go
var scratch [32]byte
n := strconv.AppendInt(scratch[:0], total, 10) // в стековый буфер — 0 аллокаций
b.Write(scratch[:n])
```

`strconv.Append*` — главный инструмент против `fmt.Sprintf` на горячем пути:
Sprintf аллоцирует минимум раз-два на вызов и ходит через reflection.

## Escape analysis: как читать `-gcflags="-m"`

Компилятор решает за вас, где живёт значение — на стеке или в куче.
Аллокации в куче — это работа GC, поэтому первый шаг оптимизации — увидеть,
что «убежало»:

```sh
go build -gcflags="-m" ./...
# ./report.go:42:13: "o.ID + \": \"..." escapes to heap
# ./report.go:44:17: out does not escape
# ./report.go:47:10: moved to heap: line
```

Типичный «плохой» фрагмент и его разбор:

```go
func line(o Order) string {
    return o.ID + ": " + strconv.FormatInt(o.Total, 10) // escapes: возвращаем наружу
}
```

`strconv.FormatInt` аллоцирует строку, результат возвращается из функции —
компилятор честно пишет `escapes to heap`. Это не баг и не «плохой код»
сам по себе: аллокация станет проблемой, только если профиль (урок 18)
показал её на горячем пути.

Как читать вывод:

- **`escapes to heap`** — аллокация в куче: результат функции переживает её
  кадр (возвращается наружу, кладётся в слайс, пересекает границу интерфейса)
  или значение слишком велико/непознаваемого размера;
- **`does not escape`** — на стеке, бесплатно;
- **`moved to heap`** — переменная «сбежала» (чаще всего — из-за замыкания
  или `fmt` с интерфейсами).

Причины побега, которые вы будете видеть постоянно: возврат указателя на
локальную переменную, передача в `interface{}` (`fmt.Println`, `json`),
присваивание в `[]any`, замыкания, размер, неизвестный компилятору.

Важно: `-m` показывает **возможность** побега, а не факт — для точного счёта
есть `-gcflags="-m=2"` и профиль аллокаций (следующий урок). И не надо
воевать с побегами ради самих побегов: одна аллокация в холодном пути
бесплатнее, чем неделя уродливого кода.

## Value против pointer: где это влияет на память

Правило первого порядка — **семантика**: указатель, если нужна мутация или
общая идентичность; значение, если копия безопасна и желаема. Память — второй
порядок:

- указатель на маленькую структуру в поле — чаще аллокация в куче + лишний
  dereference и cache miss;
- большая структура по значению — дорогой memcpy на каждый вызов;
- **слайс строк внутри структуры** по значению — не страшно: копируются
  заголовки;
- поля-примитивы в структуре (int64, bool, time.Time) — копирование дешевле
  разыменования.

Эвристика: указатели — для идентичности, интерфейсов и «опциональности»;
значения — для данных. Память решает спор, когда профиль **показал** узкое
место, а не раньше.

## sync.Pool

Пул — кэш объектов для переиспользования между горутинами: `Get`/`Put`,
потокобезопасный, но **без гарантий** — объект может быть выброшен GC в
любой момент (поэтому в пуле нельзя хранить «ценное» — только пересоздаваемое).
Классика: буферы сериализации, слайсы-скретчи, `bytes.Buffer` в горячем цикле:

```go
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

b := bufPool.Get().(*bytes.Buffer)
b.Reset()
defer bufPool.Put(b)
```

Зачем: убирает стабильный поток аллокаций → меньше работы GC → ниже хвостовые
латентности. Цена: `Get`+`Put` — это не бесплатно, а объект живёт дольше
(следствие — больше peak memory). Пул оправдан, когда профиль аллокаций
показывает одного чемпиона, аллоцируемого на каждый запрос.

## GC в двух словах

- **Триколорный марк-свип** с барьерами записи: пометить достижимое
  (белый → серый → чёрный), собрать недостижимое. Куча (heap) — та, что
  растёт и чистится; стек не участвует.
- **STW-паузы** остались на под-миллисекундном уровне (обычно < 1 мс):
  STW нужен на старте/финале циклов; в остальное время GC работает
  **конкурентно** с вашим кодом.
- **GOGC** (по умолчанию 100): цель — держать heap ≈ 2× живой памяти.
  `GOGC=200` — реже, крупнее циклы, больше памяти; `GOGC=50` — наоборот.
  Современная альтернатива — `GOMEMLIMIT` (мягкий потолок heap), обязателен
  для контейнеров с жёстким лимитом памяти:

  ```sh
  GOMEMLIMIT=1536MiB ./orders   # GC начнёт ужиматься заранее, до OOM-киллера
  ```

- **Allocs/op** в бенчмарках — счётчик аллокаций, а не байтов: 1 alloc/op
  может весить и 16 байт, и 16 МБ. Смотрите и на B/op.

Практический вывод: в Go вы управляете GC **косвенно** — числом аллокаций и
GOGC/GOMEMLIMIT. Нет `free`, нет поколений (пока), нет ручного управления —
есть «меньше мусора → меньше работы GC».

## Go vs Python

**Python:** каждый объект — «коробка» в куче: `PyObject` с refcount, даже
`int` и `float` — объекты; список — массив указателей на объекты в куче.
Память — refcount + циклический GC; кэш мелких int/str; никаких value types,
никакого стека для данных (кроме локальных ссылок). Следствие — `list[int]`
из миллиона единиц это миллион объектов-обёрток, а `sys.getsizeof` видит
только верхушку айсберга. Инструменты: `tracemalloc`, `objgraph`,
`pympler` — профиль кучи, а не аллокаций.

**Go:** примитивы и структуры живут **в значениях**: `[]int64` — сплошной
массив восьмибайтных значений, без обёрток; локальные переменные — на стеке,
бесплатно; аллокация — только когда значение «убежало». Отсюда и разница на
порядок в памяти для числовых данных.

```python
# Python: список — массив УКАЗАТЕЛЕЙ, каждый int — объект
nums = list(range(1_000_000))        # ~28 МБ + 8 МБ указателей
```

```go
// Go: сплошные 8 байт × N, данные в одном куске памяти
nums := make([]int64, 1_000_000)     // 8 МБ, одна аллокация
```

**C#:** ближе к Go — `struct` (value type, копируется) против `class`
(reference type, в куче); но у вас есть выбор явно и руками. `Span<T>` /
`Memory<T>` — stack-allocated «окно» над массивом: то, что в Go получается
естественно (слайс над массивом, срез строки), в C# достигается специальными
типами. В Go этой дихотомии синтаксически нет — её решает escape analysis,
поэтому и нужен `-m`.

## Подводные камни и анти-паттерны

1. **Конверсии `string([]byte)`/`[]byte(string)` в цикле** — каждая копирует
   данные. На горячем пути — только `Append*` и под-слайсы.
2. **`fmt.Sprintf` в цикле** — отражение + аллокации ради форматирования,
   которое `strconv` делает без единой аллокации.
3. **`make([]T, n)` без ёмкости в накопителе** — лог-линейный рост аллокаций;
   `make([]T, 0, n)` стоит одну строку.
4. **`Builder.String()` в цикле** — копия на каждой итерации; накапливайте в
   Builder, материализуйте строку один раз.
5. **Aliasing после `append`** — подлежащий массив общий, мутация через
   второй слайс «призрачно» меняет первый. Копия — `slices.Clone`.
6. **Указатели «на всякий случай»** в полях структур — лишние побеги в кучу и
   cache miss. Указатель — семантическое решение, не дефолт.
7. **`sync.Pool` ради одной аллокации на старте** — усложнение без выигрыша;
   пул окупается на стабильно горячем пути.
8. **Оптимизация без замера** — «вижу `escapes to heap`, пойду бороться»;
   профиль сначала (урок 18), правки потом.
9. **`GOGC=off` навсегда** — экономия пауз ценой безудержного роста heap и
   OOM-киллера. Вместо этого — GOMEMLIMIT и меньше мусора.

## Что делаем в капстоуне

1. Идём по горячему пути `POST /v1/orders`: валидация позиций, сериализация
   DTO — ищем и убираем конверсии в циклах, `fmt.Sprintf` на пути запроса,
   рост без ёмкости.
2. Смотрим `go build -gcflags="-m" ./...` — объясняем каждую строку «escapes».
3. Фиксируем пороги аллокаций тестами (как в практике) — регрессию
   аллокаций теперь ловит CI.
4. На следующем уроке — бенчмарки и pprof, чтобы измерить эффект.
