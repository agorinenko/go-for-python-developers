# Практика. Урок 17: память и аллокации

В пакете `optimize` — три функции с **наивными реализациями**: они корректны
(эталон поведения продублирован в `optimize_test.go`), но аллоцируют тысячи
объектов на 1000 элементов. Задание — переписать их с минимумом аллокаций.

## Задание

1. Запустите `go mod tidy && go test ./...` — увидите, как корректность
   проходит, а пороги аллокаций падают (наивные версии дают тысячи
   аллокаций/вызов).
2. Перепишите функции в `optimize/optimize.go`, **не меняя сигнатуры и
   поведение** (лекция, разделы «strings.Builder против конкатенации»,
   «Строки и []byte», «Рост слайсов»):
   - `Concat` — склейка через `", "`: вместо `+=` в цикле — одна аллокация
     под результат (`strings.Join`);
   - `BuildReport` — отчёт `"ID: total\n"`: `bytes.Buffer` с `Grow`,
     `WriteString`, `strconv.AppendInt` в стековый буфер — без конверсий
     `string ↔ []byte` в цикле;
   - `ParseIDs` — разбор CSV: под-слайсы строки не аллоцируют
     (`strings.IndexByte` + срез исходной строки), ёмкость результата —
     заранее через `strings.Count`, поля не копируются без необходимости.
3. Полезно посмотреть на вывод escape analysis по ходу:
   `go build -gcflags="-m" ./...` — найдите в нём «escapes to heap» и
   объясните себе каждую оставшуюся аллокацию.
4. Проверьте: `go test ./...` зелёный, `go vet ./...` молчит.

Пороги аллокаций (в тестах): `Concat` ≤ 3 на 1000 частей, `BuildReport` ≤ 5
на 1000 заказов, `ParseIDs` ≤ 3 на 1000 элементов. Они измерены на эталонной
оптимизации (1–2 аллокации/вызов) с запасом — не подгоняйте тесты, это
слишком легко заметить.

## Критерий сдачи

```sh
go mod tidy
go vet ./...
go test ./...
```

Всё зелёное.

## Перенос в итоговый проект

   `internal/service` и сериализация DTO в `internal/httpapi` — уберите
   конверсии `string ↔ []byte` в циклах, `fmt.Sprintf` на горячем пути,
   рост слайсов без предварительной ёмкости (`make([]T, 0, n)`).
2. Добавьте в итоговый проект тесты на пороги аллокаций для самого горячего пути
   (например, сериализация ответа `GET /v1/orders`) — по образцу
   `TestConcatAllocs`.
3. Замерьте «до/после» бенчмарком (`go test -bench` — детали на следующем
   уроке) и зафиксируйте цифры в `orders/README.md`.
