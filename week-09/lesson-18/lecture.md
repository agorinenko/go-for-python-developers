## testing.B: правила честного бенчмарка

Бенчмарк — функция `BenchmarkXxx(b *testing.B)` в `_test.go`, запускается
`go test -bench`. Go сам подбирает `b.N` для стабильного времени.

```go
func BenchmarkGenerate(b *testing.B) {
    orders := makeOrders(1000) // подготовка данных — ВНЕ таймера
    b.ReportAllocs()           // выводить B/op и allocs/op
    b.ResetTimer()             // подготовку не считаем
    for i := 0; i < b.N; i++ {
        out := reportgen.Generate(orders)
        _ = out                // использовать результат — см. ниже
    }
}
```

Правила, нарушение которых даёт цифры-враньё:

1. **`ResetTimer`/`StopTimer`/`StartTimer`** — подготовка данных, прогрев
   кэшей, инициализация считаться не должны.
2. **Результат использовать.** Компилятор выкинет мёртвый вызов — бенчмарк
   измерит «ничего». `_ = out` в цикле достаточно; для надёжности —
   `b.SetBytes` или глобальный sink (`sink = out`) с `-gcflags` не надо.
3. **Сравнивать только сопоставимое** — одна машина, одинаковые условия,
   одинаковый `-count`. Разница < 5–10% — шум, не вывод.
4. **`-count 6` + benchstat** — разброс убирается статистикой, а не глазом:

   ```sh
   go test -run '^$' -bench . -count 6 | tee before.txt
   go install golang.org/x/perf/cmd/benchstat@latest
   benchstat before.txt after.txt   # колонки: old, new, delta (с доверительным интервалом)
   ```

5. **`-benchmem`** — `B/op` (байтов) и `allocs/op`; помните, allocs ≠ байты.
6. **Не гоняйте бенчмарки в CI как тест с порогом** — они шумят на общих
   раннерах; в CI их запускают для регрессий порядка величины, а не
   процентов.

Размеры входных данных — через саб-бенчмарки, чтобы видеть асимптотику
(O(n²) узнаётся по тому, что ×10 размера даёт ×100 времени):

```go
func BenchmarkGenerate(b *testing.B) {
    for _, n := range []int{10, 100, 1000} {
        b.Run(fmt.Sprintf("n=%d", n), func(b *testing.B) {
            orders := makeOrders(n)
            b.ReportAllocs()
            b.ResetTimer()
            for i := 0; i < b.N; i++ {
                _ = reportgen.Generate(orders)
            }
        })
    }
}
```

## pprof: три профиля и как их читать

pprof — встроенный профилировщик, работает на выборке: периодически
останавливает процесс и записывает стек. Профиль **не точный счётчик**,
а статистическая выборка — выводы делаются по большим долям, а не по
дробям процента.

**CPU** (`runtime/pprof.StartCPUProfile` / флаг `-cpuprofile`):

```sh
go test -run '^$' -bench BenchmarkGenerate1000 -cpuprofile cpu.out
go tool pprof -top reportgen.test cpu.out
#      flat  flat%   sum%        cum   cum%
#   ...сколько времени функция исполнялась САМА (flat) и вместе с вызываемыми (cum)
```

Читать: ищите функции с большим **cum%** в вашем коде (не в `runtime.*`);
`flat%` — ваши собственные инструкции. Медленный `fmt.Sprintf` в профиле
виден как `fmt` + `reflect` + `runtime.convT*` — цепочка вызовов, которую
вы сами бы не заподозрили.

**Память** (`-memprofile`): два режима — `-alloc_space` (кто аллоцировал
больше всего, по умолчанию) и `-alloc_objects` (кто аллоцировал **чаще** —
обычно интереснее, аллокации по 16 байт убивают GC массой, а не весом):

```sh
go tool pprof -top -alloc_objects reportgen.test mem.out
```

**Goroutine** (`runtime/pprof.Lookup("goroutine")`) — где спят горутины,
утечки, заблокированные каналы: `go tool pprof -http :6061 g.out`.

Живой сервис отдаёт те же профили по HTTP:

```sh
go tool pprof -top http://127.0.0.1:6060/debug/pprof/heap          # кто держит память
go tool pprof -top http://127.0.0.1:6060/debug/pprof/goroutine     # где спят горутины
go tool pprof -top http://127.0.0.1:6060/debug/pprof/block         # кто ждёт каналы/мьютексы
go tool pprof -top http://127.0.0.1:6060/debug/pprof/mutex         # на чём стоим в очереди мьютекса
```

`block` и `mutex` — «спящие» профили: они требуют включённых
`runtime.SetBlockProfileRate(1)` / `SetMutexProfileFraction(1)` и отвечают
на вопрос «почему НЕ работаем», который CPU-профиль не видит в принципе.
Утечку горутин ловят сравнением `runtime.NumGoroutine()` до/после в тесте —
pprof по goroutine потом покажет, где они застряли.

**Флейм-граф** — лучший способ «увидеть» профиль:

```sh
go tool pprof -http :6060 cpu.out   # откроет веб-UI: flame graph, top, callers
```

Снизу — стек вызовов, ширина — доля времени; ищите «полки» из ваших
функций. Без гуя — `go tool pprof -flame` (или `-raw` + FlameGraph.pl).

## Профилирование живого сервиса

Для продакшен-подобных условий профиль снимают с **работающего** сервиса:

```go
import _ "net/http/pprof" // регистрирует /debug/pprof/* на DefaultServeMux

// отладочный порт, отдельный от API (не в трафик клиентов):
go func() { http.ListenAndServe("127.0.0.1:6060", http.DefaultServeMux) }()
```

```sh
go tool pprof -http :6061 http://127.0.0.1:6060/debug/pprof/profile?seconds=30
# heap, goroutine, block, mutex — там же, по аналогии
```

`runtime/pprof` — тот же механизм, но руками (нужен, если HTTP-порта нет):

```go
f, _ := os.Create("cpu.out")
pprof.StartCPUProfile(f)
// ...работаем...
pprof.StopCPUProfile()
```

Нюанс для контейнеров: профиль CPU-нагрузки снимайте во время **нагрузки** —
профиль простоя покажет только `select`/`epoll`.

## Нагрузочные инструменты

Профиль отвечает «где медленно», нагрузка — «насколько медленно под
давлением». Три практичных инструмента:

- **k6** — сценарии на JS, метрики из коробки, p95/p99, пороги в CI;
- **vegeta** — однострочник, отчёты в JSON/гистограмме;
- **oha** — простейший, хорош для быстрых замеров API.

```sh
vegeta attack -duration=30s -rate=100 < body.json | vegeta report -type=text
```

Замеряйте латентности (p50/p95/p99), ошибки и RPS до и после оптимизации —
это конечные цифры, которые пойдут в README итогового проекта.

## Методика: измерить → профилировать → оптимизировать → измерить

1. **Бенчмарк + базовый профиль.** Что доминирует? Одна функция или
   «фон» из аллокаций?
2. **Гипотеза.** «Группировка заказов по клиенту уберёт O(n²)» — гипотеза
   проверяемая, а не «попробую поправить красивое».
3. **Одна правка → один замер.** Две правки сразу — непонятно, какая
   сработала и не откатится ли «выигрыш» при следующем изменении.
4. **Проверка поведения.** Тесты корректности зелёные (в практике они —
   контракт), иначе вы оптимизировали баг.
5. **Зафиксировать.** Цифры до/после — в отчёт; профиль — рядом с ними.

Граница с преждевременной оптимизацией: вы входите в цикл **после** того,
как замер показал проблему, и выходите, когда проблема ушла. «Наверное,
это можно ускорить» без цифр — не входите.

## Go vs Python

**Python**:

```sh
python -m cProfile -o prof.out script.py      # детерминированный профиль вызовов
py-spy top --pid 1234                         # семплинг живого процесса (как pprof)
python -m memory_profiler script.py           # построчно, где растёт память
```

`cProfile` — точный, но **меняет** время исполнения (инструментовка каждого
вызова); `py-spy` — семплинг без вмешательства, ближе к pprof. Отдельная
боль: GIL и C-расширения — `cProfile` не видит время внутри numpy/C, а pprof
честно показывает нативные стеки Go.

**Go**: профилировщик встроен, почти нулевое влияние на исполнение
(семплинг), один и тот же инструмент и для тестов, и для живого процесса,
график пламени из коробки. Бенчмарки — часть стандартного набора инструментов (`testing.B`
+ `benchstat`), в Python их место занимает `pytest-benchmark`/`asv`.

**C#**: BenchmarkDotNet — эталонный бенчмарк-фреймворк (прогрев, статистика);
профили — Visual Studio/`dotnet-trace`. В Go это всё в stdlib, но
статистику `benchstat` запускаете отдельной командой — как `dotnet-trace
convert` для ETW.

## Подводные камни и анти-паттерны

1. **Бенчмарк, который компилятор выкинул** — `_ = result` забыт, цифры
   «нс на пустоту». Сверяйте с `-gcflags="-m"` или просто кладите результат
   в пакетную переменную.
2. **Выводы из одного прогона** — разброс на ноутбуке ±20%; `-count 6` +
   `benchstat`, delta с доверительным интервалом.
3. **Оптимизация функции с 2% профиля** — усилия туда, где не болит. pprof
   top-down: сначала большие куски.
4. **CPU-профиль без нагрузки** — профиль простоя показывает epoll; гоняйте
   бенчмарк или нагрузку одновременно.
5. **p99 в бенчмарке вместо распределения** — бенчмарк даёт среднее; хвосты
   смотрите под нагрузкой (k6/vegeta), они оптимизируются иначе.
6. **`debug/pprof` на публичном порту** — утечка стеков/вызовов наружу;
   отдельный интерфейс `127.0.0.1` или за аутентификацией.
7. **Микрооптимизация под конкретную машину** — `if runtime.GOARCH ==
   "arm64"` в бизнес-коде; пороги в CI ставьте с запасом (как в практике
   урока 17: ×1.5+ к эталону).
8. **`benchstat` на выбросах** — прогрев, термал, соседние процессы; если
   дисперсия огромная — сначала стабилизируйте условия, потом сравнивайте.
