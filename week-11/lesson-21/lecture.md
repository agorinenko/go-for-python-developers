# Урок 21. Ограничение частоты запросов и противодавление

## Цели урока

- понять, зачем ограничивать входящий поток и что бывает без этого;
- освоить token bucket (`golang.org/x/time/rate`) и встроить limiter в HTTP-стек как middleware (429 + `Retry-After`);

## Зачем ограничивать входящий поток

Перегрузка — это не «мало ресурсов», это **положительная обратная связь**: чем дольше сервис
отвечает, тем больше запросов в полёте (клиенты повторяют, соединения висят), тем медленнее он
отвечает. Классика: каждый запрос держит соединение с БД 2 секунды вместо 5 мс → пул
соединений исчерпан → новые запросы ждут ещё дольше → пул не освобождается никогда.

Rate limiting решает другую задачу, чем оптимизация: он **не ускоряет** сервис, он
**гарантирует** деградацию по расписанию, а не коллапс. Вы сами выбираете, где отрезать:
часть клиентов получает быстрый 429 вместо того, чтобы все получили таймаут.

Три разных механизма, которые часто путают:

| Механизм | Что ограничивает | Ответ клиенту |
|---|---|---|
| Rate limiting | темп запросов одного клиента/ключа | 429 + `Retry-After` |
| Load shedding | суммарную нагрузку на сервис (CPU, очередь) | 503, сброс очереди |
| Backpressure | скорость продюсера относительно консьюмера | замедление продюсера |

Rate limiting — про **справедливость и квоты** (у клиента есть лимит по договору), load
shedding — про **выживание** (приоритеты, отбрасываем низкоприоритетное), backpressure —
про **связанность** звеньев конвейера. В продакшене нужны все три, но включаются они в
разных местах стека.

## Token bucket: golang.org/x/time/rate

Промышленный стандарт ограничения темпа в Go — token bucket из `golang.org/x/time/rate`.

```go
import "golang.org/x/time/rate"

// 100 запросов/сек, пиковая ёмкость burst = 50 «в кредит»
limiter := rate.NewLimiter(rate.Limit(100), 50)
```

Модель: ведро ёмкостью `burst` пополняется со скоростью `r` токенов в секунду. Каждый
запрос забирает токен. Плавный поток до `r` проходит всегда; кратковременные всплески
поглощаются «кредитом» `burst`; что сверху — отклоняется. В отличие от фиксированного окна
(«N запросов за минуту») у token bucket нет жёсткой границы окна, на которой клиент может
ударить сразу после сброса счётчика.

Три метода с разной семантикой:

```go
limiter.Allow()                       // есть токен? true/false, без ожидания
limiter.Wait(ctx) error               // дождаться токена (блокировка), ctx отменяет
res := limiter.Reserve()              // резервирование «на будущее»
time.Sleep(res.Delay())               // подождать по графику лимитера
```

- `Allow` — для middleware: не хотим задерживать запросы, хотим отсечь.
- `Wait` — для фоновых исполнителей (relay outbox, экспорт): темп не важен, важно не превысить.
- `Reserve` — для клиентов, которые могут подстроить расписание (backoff-политики).

`rate.Limit` — это `float64` токенов/сек; для одной операции за 10 секунд: `rate.Every(10*time.Second)`.

## Rate limiter как middleware

В HTTP-стеке лимитер — классический middleware:

```go
func NewMiddleware(limiter Limiter, next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if !limiter.Allow() {
            w.Header().Set("Retry-After", "1")
            w.WriteHeader(http.StatusTooManyRequests)
            return
        }
        next.ServeHTTP(w, r)
    })
}
```

Ключевые детали:

1. **`429 Too Many Requests` + `Retry-After`** — это контракт с клиентом. Без
   `Retry-After` клиент не знает, когда повторить, и начнёт повторять случайно — ровно то,
   что создаёт повторные всплески. Значение — целые секунды (`"1"`) или HTTP-дата.
2. **Лимитер ставится как можно раньше** — до аутентификации? Спорно: проверка токена сама
   стоит ресурсов. Практика: грубый per-IP лимитер до auth (от DDoS-вектора), точный
   per-client (API key) — после. Два лимитера с разными бюджетами.
3. **Ключ лимитера** — то, чем идентифицируется «клиент»: IP (осторожно: NAT, IPv6-префиксы),
   API key, customer_id. Хранилище ключей: in-memory (на инстанс) или централизованное
   (Redis, урок 22).
4. **Что писать в тело ответа** — единую схему ошибок сервиса (урок 5):
   `{"error": {"code": "rate_limited", "message": "too many requests"}}`, не голый статус.

Важное ограничение: локальный `rate.Limiter` живёт в одном процессе. За балансировщиком на
10 инстансов каждый инстанс даёт полный лимит — суммарно вы пропустите 10×. Глобальный
лимит требует общей координации (Redis INCR + EXPIRE — это и есть распределённый token
bucket; готовые решения: `redis_rate`, `go-redis/redis_rate`). В итоговом проекте лимитер
локальный — этого достаточно, пока у вас один инстанс и цель «не убить БД», а не «честная
квота клиенту».

## Ограничение внутренней конкурентности: семафоры

Rate limiting отсекает **входящий** поток. Но перегрузку создаёт и внутренняя работа:
1000 запросов в секунду, каждый запускает горутину, и все они идут в пул pgx на 20
соединений. Очередь копится внутри процесса, память растёт, `context`-таймауты срабатывают
слишком поздно. Нужен лимит **одновременных** операций — семафор.

```go
import "golang.org/x/sync/semaphore"

// не более 8 одновременных обращений к каталогу
sema := semaphore.NewWeighted(8)
if err := sema.Acquire(ctx, 1); err != nil {
    return err // ctx отменён — выходим, а не копим очередь
}
defer sema.Release(1)
price, err := catalog.GetProduct(ctx, id)
```

`semaphore.Weighted` — семафор со «весами»: `Acquire(ctx, 3)` можно забрать три слота сразу
(например, по количеству соединений БД, которые займёт операция). Главное отличие от
наивного канала-семафора: **`Acquire` уважает `ctx`** — при отмене горутина не остаётся
висеть в очереди.

Для пачки задач удобнее `errgroup.SetLimit` (тот же `errgroup` из урока 8):

```go
var g errgroup.Group
g.SetLimit(5) // не более 5 одновременных горутин
for _, job := range jobs {
    g.Go(func() error { return job() })
}
if err := g.Wait(); err != nil { ... } // первая ошибка
```

`SetLimit` — это встроенный семафор внутри `errgroup`: `g.Go` **блокируется**, пока не
освободится слот. То есть вызов `Go` в цикле сам по себе становится точкой backpressure:
продюсер задач не может уйти вперёд дальше, чем на `limit` задач. Это и есть связка
«лимит одновременности = управление очередью».

## Backpressure в конвейерах (закрепление урока 6)

На уроке 6 мы строили конвейеры на каналах. Классическая ошибка, которая возвращается в
продакшене: читать вход быстрее, чем обрабатываешь:

```go
// анти-паттерн: неограниченный буфер — очередь копится, память утекает,
// продюсер не узнаёт о проблеме никогда
jobs := make(chan Job) // небуферизованный — ок, но продюсер встаёт навсегда
inbox := make(chan Job, 1_000_000) // «пусть буферизуется» — это не решение
```

Правило конвейера: **продюсер должен блокироваться на самом медленном звене**. Варианты:

1. Небуферизованный канал — естественный backpressure, но малейшая неравномерность
   останавливает весь конвейер.
2. Маленький буфер + `select` с `ctx.Done()` и таймаутом на запись — «если не влез за 100 мс,
   отбрасываем/возвращаем 503» (это уже load shedding).
3. `errgroup` + `SetLimit` + общий входной канал: N исполнителей тянут задачи в своём темпе,
   продюсер пишет в канал и блокируется, когда все исполнители заняты.

Выбор между ними — политика: терять запросы нельзя → жди (вариант 1/3); лучше потерять
часть, чем умереть → вариант 2. Для очередей сообщений (Kafka) backpressure «бесплатный»:
продюсер не коммитит offset, пока пакет не обработан — консьюмер читает не быстрее, чем
обрабатывает, по построению (неделя 8).

## Таймауты на каждом слое (закрепление урока 9)

Ограничители конкурентности бесполезны, если операции могут висеть вечно. Таймаут должен
быть на **каждом** переходе между компонентами:

| Слой | Таймаут | Типичное значение |
|---|---|---|
| reverse proxy → сервис | `http.Server.ReadHeaderTimeout`, `IdleTimeout` | 5 с / 60 с |
| обработчик → БД | `ctx` в `pgxpool.Query` | 2–5 с |
| обработчик → каталог (gRPC) | `context.WithTimeout` в клиенте | 1–2 с |
| сервис → Redis | `redis.Options.ReadTimeout/WriteTimeout` | 200–500 мс |
| обработчик целиком | `http.Server.WriteTimeout` | 10 с |

Железное правило: **таймаут вызывающего меньше таймаута вызываемого** (иначе вызывающий
повторяет запрос, который ещё выполняется — идемпотентность под ударом). Сумма таймаутов
на пути запроса должна укладываться в обещанную клиенту латентность.

`http.Server` таймауты — отдельная тема: без `ReadHeaderTimeout` сервер уязвим к
slowloris-подобным атакам (клиент держит соединение, отправляя заголовки по байту).
В итоговом проекте они уже заданы с недели 5 — на этом уроке мы просто проверяем, что
внешние вызовы не используют `context.Background()`.

## Panic/recover на границе сервиса (закрепление урока 9)

Под нагрузкой всплывают паники, которых не было в тестах: `index out of range` на гонке,
nil-указатель из-за гонки развёртывания. Паника в одном обработчике **не должна ронять процесс** —
но и не должна маскироваться:

```go
func Recovery(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                if err, ok := rec.(error); ok && errors.Is(err, http.ErrAbortHandler) {
                    panic(err) // клиент ушёл — не притворяемся, что что-то можно ответить
                }
                // лог со стеком (урок 19: slog + debug.Stack())
                w.WriteHeader(http.StatusInternalServerError)
                // + единая схема ошибки
            }
        }()
        next.ServeHTTP(w, r)
    })
}
```

`http.ErrAbortHandler` — специальная паника из `net/http`: её обязаны **перебрасывать**,
иначе сломаете обработку отключившегося клиента. `recover` только на границе — внутри
бизнес-логики паники по-прежнему запрещены (урок 2).

## Graceful degradation

Цель всех механизмов урока — чтобы при дефиците ресурсов сервис **продолжал отвечать** на
часть запросов осмысленно, а не падал целиком. Лестница деградации для `orders`:

1. Полная функциональность.
2. Отключаем дорогие фичи: проверка цены в каталоге → отвечаем кэшем или «цена неизвестна»
   (с пометкой в ответе).
3. Read-only: `POST /v1/orders` возвращает 503, чтение работает.
4. Только healthcheck и 429/503 для всего остального.

Каждая ступень — это **осознанное решение**, закодированное заранее (флаги, бюджет
таймаутов, circuit breaker с урока 14), а не случайный результат медленных зависимостей.
Circuit breaker и rate limiting — две стороны одного: breaker защищает от **сломанной**
зависимости, limiter — от **слишком быстрого** входящего потока.

## Go vs Python

**FastAPI**: ограничение темпа делается библиотекой `slowapi` (обёртка над `limits`):

```python
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter

@app.get("/orders")
@limiter.limit("100/minute")          # декларативно, стратегия в строке
async def list_orders(request: Request): ...

# 429 + Retry-After slowapi отдаёт сам, кастомизация — exception handler
```

Декларативный стиль удобен, но «стратегия как строка» парсится в среде выполнения — опечатку
`"100/minutes"` вы увидите в проде, а не при старте. В Go стратегия — это типы и константы:
`rate.NewLimiter(rate.Limit(100), 50)` не даст опечататься.

**Ограничение конкурентности**: `uvicorn --limit-concurrency 50` ограничивает число
одновременно обрабатываемых запросов **на уровне сервера** — единая ручка для всех
обработчиков. В Go аналога «из коробки» нет: мы ограничиваем точечно — семафором именно
вокруг БД, лимитером именно на этом маршруте. Это и плюс (гибкость), и минус (легче
забыть); дисциплину создаёт ревью.

**aiohttp-клиент** даёт per-host лимиты соединений из коробки:

```python
conn = aiohttp.TCPConnector(limit_per_host=20)
timeout = aiohttp.ClientTimeout(total=5)
```

В Go `http.Client` по умолчанию **не ограничивает** число соединений к хосту
(`http.Transport` с `MaxConnsPerHost`/`MaxIdleConnsPerHost` — руками). Для внутренних
вызовов лимит на клиенте часто важнее лимита на сервере: так вы не устраиваете
thundering herd собственными руками.

**Семафоры**: `asyncio.Semaphore(5)` — прямой аналог `semaphore.NewWeighted(5)`, с тем же
паттерном `async with sem:`. Разница — `ctx` против `Task.cancel()`: в Go отмена приходит
как отмена контекста и `Acquire` обязан её уважать, в asyncio — как `CancelledError`,
которую легко проглотить.

## Подводные камни и анти-паттерны

1. **Лимитер в тестах — источник флаппи.** Тесты, проходящие через реальный limiter с
   rate=1, зависят от таймингов. В тесты лимитер подавайте фейком (`allowAll`/`denyAll`),
   а сам `TokenBucket` тестируйте burst-поведением без ожиданий (rate 1000, burst 2:
   третий вызов отклонён — детерминированно, без sleep).
2. **`Allow()` вместо `Wait()` в фоновых задачах.** Воркер, который «пропускает» работу,
   когда нет токена, теряет данные. Для фоновой работы — `Wait(ctx)`: пусть подождёт,
   темп важнее мгновенности.
3. **429 от собственных внутренних вызовов.** Если ваш API-шлюз лимитирует всех подряд,
   межсервисные вызовы тоже получат 429. Внутренний трафик либо не лимитируется, либо
   лимитируется отдельным, более щедрым бюджетом.
4. **Ретраи без backoff — усилитель перегрузки.** 100 клиентов получают 429 и все
   повторяют через 100 мс — новый всплеск. `Retry-After` + jitter в клиенте (урок 14).
5. **Локальный лимитер за балансировщиком.** N инстансов = N× лимита. Нужна глобальная
   квота — координация через общее хранилище, а не локальный `rate.Limiter`.
6. **`errgroup.SetLimit(0)`** — бесконечное ожидание слота; `limit` обязан быть ≥ 1
   (проверяйте в конструкторе/конфиге).
7. **Первая ошибка в `errgroup` отменяет общий `ctx`** (`errgroup.WithContext`) — все
   исполнители, честно проверяющие `ctx`, завершатся, но `g.Go` из цикла-продюсера может
   заблокироваться навсегда, если его никто не отменяет. Продюсер должен тоже слушать `ctx`.
8. **`Recover` глотает `http.ErrAbortHandler`** — см. выше; перебрасывайте её паникой.
9. **Таймаут на слое БД больше таймаута обработчика** — запрос «отменён» для клиента, но
   транзакция живёт и держит соединение. Таймауты должны быть вложенными: обработчик >
   БД > клиент.
10. **Лимитирование без метрик.** Без счётчика 429 вы не узнаете, что лимит душит
    легитимных клиентов. Prometheus-метрика на каждый отказ (урок 20) — обязательна.

## Что делаем в итоговом проекте

1. Создаём `orders/internal/ratelimit`: `Limiter`, `TokenBucket` (на `x/time/rate`) и
   `NewMiddleware` — код из практики переносится почти без изменений.
2. Включаем middleware в цепочку `internal/httpapi` (порядок: request ID → logging →
   recovery → **rate limit** → маршрутизатор); ключ лимитера — IP клиента, бюджет из
   конфига.
3. Ограничиваем внутреннюю конкурентность: `errgroup.SetLimit` на валидации позиций
   (неделя 3) и семафор вокруг обращений к каталогу.
4. Добавляем метрику `http_requests_limited_total` и проверяем 429 под нагрузкой.
