# Урок 22. Кэширование и масштабирование

## Цели урока

- освоить cache-aside: когда читать мимо кэша, когда прогревать, как инвалидировать;
- понять проблему thundering herd/stampede и закрыть её `singleflight`;
- разобрать Redis как кэш-хранилище: базовые команды, TTL, пайплайны, `go-redis`;
- спроектировать горизонтальное масштабирование: stateless-сервисы, шардирование,
  почему избегают sticky sessions;
- усвоить главное правило кэша: **сначала измерь**.

## Задача из капстоуна

`GetOrder` стал самым горячим маршрутом `orders`, и каждая его миллисекунда — это
нагрузка на PostgreSQL. На неделе 4 мы сделали in-memory кэш с блокировками; теперь
задача вырасти: кэш должен переживать рестарты и разделяться между инстансами — это
Redis, — а чтение из БД нужно защитить от «слона в посудной лавке»: 100 одновременных
промахов по одному ключу не должны превращаться в 100 одинаковых SELECT. Контракт
недели — в [CAPSTONE.md](../../CAPSTONE.md): `internal/cache` + singleflight в сервисе.

## Cache-aside: самый честный паттерн кэширования

Cache-aside (он же lazy loading): приложение само решает, когда читать кэш, а когда —
источник.

```
Get(key):
    v, ok := cache.Get(key)      // 1. сначала кэш
    if ok: return v
    v, err := repo.Get(key)      // 2. промах — источник
    if err: return err
    cache.Set(key, v, ttl)       // 3. прогрели кэш
    return v
```

Свойства паттерна:

- **Кэш никогда не блокирует источник.** Кэш упал — сервис продолжает работать, просто
  медленнее. Это отличает кэш от БД: доступность кэша не критична, критична его
  корректность.
- **В кэш попадает только то, что реально спрашивали.** Нет превентивного прогрева
  (в отличие от write-through/write-behind, где пишется всё подряд).
- **Первое чтение всегда медленное** — это цена ленивости. Холодный старт после деплоя:
  кэш пуст, вся нагрузка бьёт в БД. Если это больно — прогревайте выборочно (топ-N ключей
  из метрик), а не всё.
- **Инвалидация — на писателе**: обновили заказ → `Del(key)` (или `Set` нового значения).
  Никогда не «поправляйте» кэш на месте в надежде, что значение совпадёт с БД: два разных
  пути записи — два источника рассинхрона.

Сравнение паттернов одним экраном:

| Паттерн | Кто пишет в кэш | Инвалидация | Когда |
|---|---|---|---|
| Cache-aside | читатель (после промаха) | писатель делает Del | по умолчанию |
| Read-through | кэш сам (за ним источник) | как у cache-aside | читаемая конфигурация |
| Write-through | писатель (и в кэш, и в источник) | не нужна (но частичные сбои!) | строгая свежесть |
| Write-behind | писатель (только кэш, асинхронный сброс) | не нужна | выдерживаем потери |

## TTL: почему кэш без срока жизни — бомба

Каждое значение в кэше обязано иметь TTL. Без TTL:

- старые данные живут вечно — «инвалидация» становится ручной работой после каждого
  изменения схемы;
- память Redis растёт неограниченно (maxmemory с политикой eviction — это уже другой
  сервис, а не кэш);
- после бага в коде записи отравленное значение не уйдёт само.

Выбор TTL — компромисс: длинный TTL = редкие промахи, но долгое окно неконсистентности;
короткий = свежее данные, но больше нагрузки на источник. Отправная точка для
капстоуна: 30–60 секунд для заказов (свежесть статусов важна), плюс **явная**
инвалидация на каждую запись — TTL тогда работает как страховка, а не как механизм
консистентности.

## Thundering herd и singleflight

Самый болезненный случай cache-aside — stampede: кэш холодный (или истёк TTL), и N
параллельных запросов одного ключа одновременно промахиваются и одновременно идут в
источник. Для `orders` это выглядит так: рестарт сервиса → 1000 одинаковых
`SELECT ... WHERE id = $1` → БД встаёт → сервис получает таймауты → «перегрузка без
причин» (урок 21).

`golang.org/x/sync/singleflight` дедуплицирует **одновременные** вызовы с одинаковым
ключом: источник вызывается один раз, все остальные получают тот же результат:

```go
import "golang.org/x/sync/singleflight"

var sf singleflight.Group

func (c *Cache) Get(ctx context.Context, key string) ([]byte, bool, error) {
    // ...проверка локального кэша (быстрый путь для hit)...

    res, err, _ := sf.Do(key, func() (any, error) {   // один вызов на ключ
        // ПОВТОРНАЯ проверка кэша внутри полёта! Между первой проверкой и
        // вызовом Do прошло время: другой полёт мог уже заполнить ключ —
        // без повторной проверки источник вызовется дважды.
        if v, ok := c.localGet(key); ok {
            return v, nil
        }
        value, ok, err := c.backend.Get(ctx, key)     // источник
        if err != nil || !ok {
            return nil, err
        }
        return value, c.fill(key, value)              // прогрев кэша внутри полёта
    })
    if err != nil {
        return nil, false, err
    }
    v, _ := res.([]byte)
    return v, v != nil, nil
}
```

Что важно понимать про `singleflight`:

1. Дедупликация — **только в окне полёта запроса**. Запрос завершился — следующий промах
   снова идёт в источник (если не прогрели кэш). Поэтому прогрев кэша — часть той же
   функции, а не «потом».
2. **Проверку кэша повторяют внутри полёта.** Между проверкой «снаружи» и входом в
   `Do` есть окно: другой полёт мог уже заполнить ключ. Без повторной проверки под
   нагрузкой источник вызывается дважды — ровно то, от чего мы защищаемся.
   Паттерн — double-checked locking, знакомый вам по C#/Java.
3. Ключ дедупликации — строка. Кэшировать интернированный ключ (`"order:" + id`)
   — обычная практика; коллизии ключей по построению совпадают с коллизиями кэша.
4. `Do` возвращает `(v, err, shared)` — `shared=true` означает «результат разделён с
   другими горутинами»; удобно для метрик (сколько раз singleflight спас БД).
5. Отмена контекста одного из ожидающих **не отменяет** общий полёт — источник вызван
   одним `ctx` (первым). Если тот `ctx` истечёт, ошибку получат все. Для чувствительных
   сценариев есть `DoChan` и `Forget` (вручную выбросить закешированный полёт).
6. `singleflight` лечит только **одинаковые ключи**. 1000 промахов по 1000 разным ключам
   (загрузка списка) он не дедуплицирует — там нужен лимит конкурентности (семафор,
   урок 21) и пакетная загрузка.

## Redis как кэш-хранилище

In-memory кэш недели 4 умирает вместе с процессом и не разделяется между инстансами.
Промышленный кэш-слой — Redis. Клиент для Go — `github.com/redis/go-redis/v9`
(контекстный, с пулом соединений и пайплайнами):

```go
client := redis.NewClient(&redis.Options{
    Addr:         "redis:6379",
    ReadTimeout:  300 * time.Millisecond, // кэш обязан быть быстрым или выключаться
    WriteTimeout: 300 * time.Millisecond,
    PoolSize:     10,
})

// SET с TTL — атомарно: значение и срок жизни
err := client.Set(ctx, "order:o-1", payload, 30*time.Second).Err()
v, err := client.Get(ctx, "order:o-1").Bytes()
if errors.Is(err, redis.Nil) { // ключа нет — это НЕ ошибка
    // miss
}
err = client.Del(ctx, "order:o-1").Err()
```

Три вещи, которые отличают кэш на Redis от «ещё одной БД»:

1. **`redis.Nil` — штатный ответ** «ключа нет». Ловить его через `errors.Is`, а не
   `err != nil` — иначе промах превратится в ошибку сервиса.
2. **Сериализация — ваша забота.** Значение — `[]byte`. Для заказов — `json.Marshal`
   (просто, читаемо) или protobuf (компактнее, быстрее; контракт уже есть с недели 7).
   Один раз выбрав формат, заморозьте его: сменили схему — старые ключи нужно вычищать
   или версионировать (`v2:order:`).
3. **Отказ Redis — не повод падать.** Cache-aside это и так переживает: промах уходит в
   источник. Но время ответа деградирует — ограничивайте его таймаутом (см. выше) и
   считайте метрику ошибок кэша. Кэш с 50% ошибок — это накладные расходы, а не
   ускорение.

**Пайплайны** — способ амортизировать RTT: серия команд уходит одним пакетом.

```go
pipe := client.Pipeline()
for _, id := range ids {
    pipe.Get(ctx, "order:"+id) // команды копятся, в сеть не уходят
}
cmds, err := pipe.Exec(ctx) // один round-trip
for _, cmd := range cmds {
    v, err := cmd.(*redis.StringCmd).Bytes()
    // ...
}
```

Паттерн «запросить 100 ключей одним round-trip» — обязателен для `ListOrders`:
без пайплайна 100 `Get` = 100 RTT ≈ 100 мс, с пайплайном — один RTT. Аналог —
`SELECT ... WHERE id IN (...)` в SQL.

## Горизонтальное масштабирование

Кэш — это ещё и про масштабирование **сервиса**, а не только данных.

1. **Stateless-сервисы.** Весь смысл кэша на Redis в том, что инстансы orders не хранят
   состояние локально: любой запрос может попасть на любой инстанс. Локальный кэш недели
   4 остаётся как L1 (наносекунды, но неразделённый и холодный после рестарта), Redis —
   L2. Двухуровневая схема: L1 hit ~ наносекунды, L2 hit ~ 0.1–1 мс, промах — БД.
2. **Шардирование ключей.** Когда Redis перестаёт помещаться на одном узле — шардируйте
   по ключу (Redis Cluster делает это сам: слот = crc16(key) % 16384). Ключи проектируйте
   так, чтобы связанные данные лежали в одном слоте (hash tags), а не размазывались.
3. **Sticky sessions — избегать.** «Приклеивание» клиента к инстансу возвращает сервису
   состояние: инстанс нельзя убить (клиент потеряет сессию), нельзя перебалансировать,
   деплой теряет часть клиентов. Если состояние нужно — оно идёт в общее хранилище
   (Redis, БД), а не в память инстанса. Исключение — консьюмеры Kafka с партициями
   (там «приклейка» диктуется партицией и это нормально).

## Консистентность: eventual по построению

Кэш вводит окно неконсистентности: между записью в БД и инвалидацией кэша читатель
видит старое значение. Это **eventual consistency** в самом жёстком смысле — окно
маленькое (миллисекунды, если инвалидация в той же транзакции/сразу после), но оно есть.

Как держать окно минимальным:

- инвалидация **сразу после** коммита записи (не «когда-нибудь»);
- для заказов в капстоуне: после `UpdateStatus` — `Del`; после `CreateOrder` — можно
  ничего не чистить (нового ключа в кэше нет), если не кэшируете списки;
- списки кэшируйте отдельно и инвалидируйте по «семейству» ключей (префикс + SCAN или
  набор ключей) — тут и помогает версионирование ключей;
- событие инвалидации можно слать через Kafka (неделя 8): другие инстансы узнают о
  записи — но помните, что событие доедет позже, окно всё равно есть.

Правило честности: если продукт требует строгой согласованности чтения (например,
баланс счёта), кэшировать это место нельзя — читайте из БД. Кэш — для данных, где
«чуть устаревшее» приемлемо и оговорено.

## Когда кэш НЕ нужен

Кэш — это вторая система хранения со своей моделью инвалидации, то есть новый класс
багов (stale read — классика «почему заказ виден со старым статусом»). Поэтому правило
номер один: **сначала измерь** (pprof, метрики, уроки 17–18). Кэшировать стоит, когда:

- чтений многократно больше записей;
- источник реально узкое место (измерено, а не предположено);
- данные терпимы к отставанию.

Не кэшируйте: данные с жёсткими требованиями согласованности; ключи с равномерно
уникальным доступом (каждый запрос — новый ключ: кэш только добавляет RTT и память);
большие бинарные объекты (для них — object storage, не Redis). И помните про
**негативное кэширование** как отдельное решение: если «ключа нет» — тоже дорогой ответ
источника, кэшируйте и его, но с коротким TTL и только там, где отсутствие — частый
случай.

## Go vs Python

**redis-py / aioredis**: та же модель команд, но клиент синхронный или asyncio-дуплекс:

```python
import redis.asyncio as aioredis

r = aioredis.from_url("redis://redis:6379")
await r.set("order:o-1", payload, ex=30)          # TTL в секундах
v = await r.get("order:o-1")
await r.delete("order:o-1")
```

`go-redis` концептуально идентичен: `Set(ctx, key, val, ttl)`. Разница — в отмене: в
Go `ctx` проброшен в **каждую** команду, в aioredis — `Task.cancel()` и ловля
`CancelledError` вокруг await. Одна и та же семантика «таймаут на команду», разные
механизмы.

**`functools.lru_cache`** — in-process кэш без TTL и без конкурентной дедупликации:

```python
from functools import lru_cache

@lru_cache(maxsize=1024)          # maxsize=None — утечка памяти «легально»
def get_order(order_id: str) -> dict: ...
```

`lru_cache` кэширует по hash-аргументов, вытесняет LRU, но: не умеет TTL, не знает про
инвалидацию (только `cache_clear()` на всё сразу), а главное — **не решает stampede**:
10 потоков одновременно вызовут `get_order("o-1")` → 10 обращений в БД. `singleflight`
в Python нужно собирать самому (asyncio-локи по ключу) — в Go это одна строка из
`x/sync`. Аналог `lru_cache` в Go — самодельный map+mutex (неделя 4) или
`hashicorp/golang-lru`, но без TTL и singleflight это всё ещё половинчатое решение.

**uvicorn workers**: `--workers 4` = 4 процесса = **4 независимых локальных кэша**.
Каждый процесс греет кэш сам, инвалидация в одном процессе невидима остальным —
именно поэтому в Python-стеках кэш почти сразу выносят в Redis. В Go с его горутинами
один процесс съедает все ядра — локальный кэш один на инстанс, но при нескольких
инстансах проблема та же: L1 разъезжается, поэтому L2 в Redis нужен и Go-сервису.
Разница в масштабе, а не в существе.

## Подводные камни и анти-паттерны

1. **Кэширование ошибок.** `backend.Get` вернул ошибку — не пишите её в кэш и не
   «кэшируйте неудачу»: иначе короткий сбой БД заморозится на весь TTL. Ошибки
   пробрасываются наверх, кэш остаётся холодным.
2. **Кэширование «отсутствия» без негативного кэша.** Если отсутствие ключа — частый и
   дорогой ответ, кэшируйте его осознанно (короткий TTL), а не случайно.
3. **Один `Get` — один RTT.** В циклах — только пайплайны/MGET, иначе кэш медленнее БД.
4. **`err != nil` вместо `redis.Nil`.** Промах — штатный ответ, не ошибка сервиса
   (см. выше). Классика: «Redis лежит» в алертах, а на деле — все запросы мимо кэша.
5. **Инвалидация в другом месте кода, чем запись.** Записей в БД три (create/update/
   delete) — инвалидаций должно быть три. Пропущенная — stale read до конца TTL.
6. **Ключи без схемы и версии.** `"o-1"`, `"order_1"`, `"order:1"` — зоопарк; заведите
   один формат (`order:{id}`) и константу-функцию ключа. Смена схемы значения — новая
   версия ключа.
7. **Большие значения.** Мегабайтные значения в Redis фрагментируют память и убивают
   RTT. Кэш — для маленьких горячих объектов.
8. **Кэш как источник правды.** Потеря Redis не должна терять данные (для этого —
   persistence и реплики, но это уже хранилище, а не кэш). Кэш всегда пересоздаваем из
   источника.
9. **Stampede после каждого деплоя.** Холодный кэш + всплеск = полная нагрузка на БД.
   singleflight сглаживает, но не отменяет: подумайте о прогреве или о переносе кэша
   между версиями (в капстоуне — отложим, осознанно).
10. **TTL = 0.** `Set` без TTL в Redis хранит ключ вечно. В go-redis нулевой `ttl`
    именно это и делает — проверяйте конфиг на 0.

## Что делаем в капстоуне

1. В `orders/internal/cache` добавляем поверх кэша недели 4 слой `Cache` с `singleflight`
   (код из практики переносится почти как есть).
2. Реализуем `Backend` для Redis (`go-redis`): `Get`/`Set`/`Del` с таймаутами из конфига;
   `internal/cache` использует его как L2, in-memory кэш недели 4 — как L1.
3. Подключаем кэш в `GetOrder` сервисного слоя; ключ — `order:{id}`, сериализация — JSON
   (доменная модель недели 1), TTL — 30 с + инвалидация в `UpdateStatus`/`CancelOrder`.
4. Метрики: hit/miss ratio, ошибки Redis, счётчик `shared` из singleflight (урок 20).
5. Проверка под нагрузкой (k6, урок 18): после прогрева — 99-й перцентиль на `GetOrder`
   без запросов в PostgreSQL.
