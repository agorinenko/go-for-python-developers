## Почему «просто вызвать» недостаточно

Внутри одного процесса вызов функции либо сработал, либо вернул ошибку —
сразу. Вызов по сети имеет пять исходов вместо двух: успех, быстрый отказ,
медленный отказ, отказ «в никуда» (пакет потерян), и успех, который мы
не увидели (ответ потерян). К этому добавьте перегрузки: если сервис A
хронически ждёт медленный сервис B, он копит горутины/сокеты, растёт его
собственная задержка, и так по цепочке — **каскадный отказ**. Стандартные
ответы индустрии, которые мы строим сегодня:

1. **Таймауты/дедлайны** — не ждать вечно;
2. **Retry** — пережить кратковременный сбой;
3. **Идемпотентность** — сделать повтор безопасным;
4. **Circuit breaker** — не звонить в заведомо мёртвую зависимость.

## Retry с backoff и jitter

Наивный retry — «ошибка? повторить немедленно» — под нагрузкой делает
только хуже: все клиенты долбят упавший сервис одновременно. Правильный
вариант:

```go
type RetryPolicy struct {
    MaxAttempts int           // включая первую попытку
    BaseDelay   time.Duration // база задержки
    MaxDelay    time.Duration // потолок экспоненты
}

for attempt := 1; attempt <= maxAttempts; attempt++ {
    err := fn(ctx)
    if err == nil || !IsRetryable(err) {
        return err
    }
    delay := time.Duration(1<<uint(attempt-1)) * policy.BaseDelay
    if delay > policy.MaxDelay || delay <= 0 {
        delay = policy.MaxDelay
    }
    jittered := time.Duration(rand.Int64N(int64(delay) + 1))
    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-time.After(jittered):
    }
}
```

Три решения, каждое из которых обязано:

- **Exponential backoff**: задержка растёт (`1s, 2s, 4s...`) — не даём
  сервису добить себя и даём ему время восстановиться. Потолок
  `MaxDelay` — экспонента не взлетает в часы.
- **Jitter** — случайная составляющая задержки. Без неё тысяча клиентов,
  стартовавших одновременно, повторит попытки **синхронными волнами** —
  ровно то, от чего лечились. Канонический разбор — статья AWS
  Architecture Blog про retry и jitter (ссылка в материалах).
  Варианты: full jitter (равномерно `[0, delay]`), equal jitter
  (`delay/2 + [0, delay/2]`). Full jitter прост и почти всегда достаточен.
- **Классификация ошибок**: повторять можно только то, что безопасно.
  `4xx` (невалидный запрос) не станет валидным от повтора; `InvalidArgument`
  из gRPC — то же. Повторяем таймауты, `Unavailable`, разорванные
  соединения, `5xx` без побочных эффектов. Классификацию несёт вызывающий
  код — в практике это обёртка `RetryableError` + `errors.Is`-совместимый
  `IsRetryable`.

**Идемпотентность** — предусловие retry: повтор операции не должен дать
второй заказ. Идемпотентность строится на уровне API (ключ идемпотентности,
уникальные ID от клиента, `If-Match`) — retry лишь эксплуатирует её.
Повторять неидемпотентную операцию нельзя никогда, как бы ни хотелось.

Контекст в retry: ожидание обязано слушать `ctx.Done()` — отмена клиента
должна прерывать и паузу, а не только сам вызов. `ctx.Err()` из fn
возвращается сразу, без повторов: клиент ушёл.

## Таймауты против дедлайнов

Таймаут — «сколько ждём ответа». Дедлайн — «когда операция обязана
завершиться целиком», и он **распространяется**: `context.WithDeadline`
пробрасывается сквозь вызовы, и каждый сервис в цепочке знает, сколько
времени у него осталось. В gRPC дедлайн — часть протокола (grpc-timeout
в заголовках), сервер получает его в `ctx` автоматически:

```go
ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second) // дедлайн вызову
resp, err := catalogClient.GetProduct(ctx, &catalogpb.GetProductRequest{Id: id})
```

Правила:

- Дедлайн на **каждый** исходящий вызов. «Дедлайн всего запроса» в
  HTTP-хэндлере — не замена: каждая ножка цепочки должна иметь свой
  лимит, иначе один медленный сосед съедает весь бюджет.
- Бюджет дедлайнов: сумма таймаутов цепочки ≤ бюджет запроса (клиент
  ждёт 3s, а вы внутри ждёте соседа 5s — бессмысленно).
- Уважать входящий дедлайн: сервер должен проверять `ctx.Err()` (урок 13,
  стриминг) и возвращать `DeadlineExceeded`, а не работать после отмены.
- gRPC-коды: `DeadlineExceeded` означает «истекло у нас», и его обычно
  ретраят (осторожно — если дедлайн сработал по вине медленного сервиса,
  повтор усугубит); `Canceled` — клиент ушёл, повторять бессмысленно.

## Circuit breaker

Retry лечит **кратковременные** сбои; breaker — **длительные**. Если
каталог лежит пять минут, retry всё это время молотит его запросами и
жрёт наш лимит дедлайна. Breaker размыкает цепь: вызовы не выполняются
вовсе.

```go
type State int

const (
    StateClosed State = iota // нормальная работа
    StateOpen                // вызовы отклоняются
    StateHalfOpen            // один пробный вызов
)

cb := NewCircuitBreaker(threshold: 5, openTimeout: 30*time.Second)

err := cb.Call(ctx, func(ctx context.Context) error {
    _, err := catalogClient.GetProduct(ctx, &catalogpb.GetProductRequest{Id: id})
    return err
})
if errors.Is(err, resilient.ErrCircuitOpen) {
    // зависимость лежит — быстрый отказ, возможно, деградация сервиса
}
```

Три состояния:

- **Closed** — нормальная работа. Счётчик подряд идущих ошибок; `threshold`
  ошибок подряд → **Open**.
- **Open** — вызовы отклоняются мгновенно (`ErrCircuitOpen`), без сети.
  Так держится `openTimeout`.
- **Half-open** — по истечении `openTimeout` допускается **один**
  пробный вызов: успех → Closed (счётчик сброшен), ошибка → снова Open
  (таймер сначала). Полуоткрытое состояние — способ «проверить, не
  ожила ли зависимость», не заливая её трафиком.

Реализация — конечный автомат под мьютексом: в Open проверяем таймер
(`time.Since(openedAt) < openTimeout` → отказ), в Half-open выполняем
пробный вызов и по результату переходим, в Closed считаем ошибки подряд.
Никакой магии: ~40 строк кода, которые вы напишете в практике.

Нюансы, которые редко попадают в «книжные» реализации:

- **Успех сбрасывает счётчик**, а не уменьшает: три ошибки подряд — порог,
  но «ошибка, успех, ошибка, успех...» — работа с флапами, цепь не рвём.
- **Отмены — не отказы**: `context.Canceled`/`DeadlineExceeded` из
  клиентского контекста не считаются (клиент сам ушёл; зависимость не
  виновата). Частая ошибка — размыкать цепь на таймаутах, выставленных
  самим клиентом.
- **Half-open допускает один вызов**: в учебной реализации мутекс держит
  весь вызов; в промышленной — пробный вызов помечается отдельно, чтобы
  параллельные запросы не проскочили толпой.
- **Пороги — данные, не магия**: `threshold=5`, `openTimeout=30s` для
  нашего клиента каталога — стартовые значения; в проде их подбирают по
  нагрузке и SLO зависимости.

Порядок сборки: **breaker снаружи retry** — пока цепь разомкнута, нечего
повторять; retry внутри — для коротких сбоев в closed-состоянии. И оба —
внутри дедлайна: суммарное время всех попыток обязано умещаться в бюджет
запроса (backoff с потолком `MaxDelay` и ограниченным `MaxAttempts`
именно поэтому).

## Go vs Python: tenacity, httpx, pybreaker

```python
# tenacity: retry с backoff+jitter декларативно
@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.05, max=1) + wait_random(0, 0.05),
    retry=retry_if_exception_type(httpx.ConnectError),
)
async def get_product(product_id: str): ...
```

Python закрывает тему библиотеками: `tenacity` (декораторы retry),
`httpx` (встроенные retries), `pybreaker` (circuit breaker),
`urllib3.Retry` (количество, backoff, статусы). В Go стандартной
библиотеки для этого нет, и это осознанно: примитивы маленькие (наша
практика — ~150 строк), а семантика зависит от транспорта и команды.
Зато в Go нет декораторов — retry оборачивает `func` явно, и `ctx` —
часть сигнатуры, а не магия фреймворка.

Разница видна и в классификации ошибок: в Python тип исключения и есть
классификатор (`retry_if_exception_type(ConnectError)` — повторяем только
ошибки соединения); в Go ошибка-значение несёт метку (`RetryableError` +
`errors.Is`), и та же классификация выражается явным решением в точке,
где ошибка возникает: пометил — повторим, не пометил — нет. Оба подхода
корректны; Go-вариант не требует исключений и работает сквозь `%w`-обёртки.

**C#**: Polly — ближайший аналог tenacity (policy, retry, circuit
breaker) и одновременно пример того, как та же задача решается
декларативно. Go-вариант — минимальный императивный код, который проще
ревьюить построчно.

## Подводные камни и анти-паттерны

1. **Retry без jitter** — синхронные волны повторных запросов; под
   нагрузкой это вторая атака на сервис.
2. **Retry 4xx** — невалидный запрос повтором не починить; зато можно
   сделать двойное списание, если 4xx пришёл после сайд-эффекта.
3. **Retry без идемпотентности** — дубликаты заказов в базе. Сначала
   идемпотентность, потом retry.
4. **Бесконечный retry** — без `MaxAttempts` и `MaxDelay` повтор
   превращается в вечный цикл, замаскированный под «надёжность».
5. **Таймаут на каждый вызов забыт** — один зависший сосед держит
   пул соединений; дедлайн обязателен на каждой ножке цепочки.
6. **Breaker на отменах** — размыкание цепи по `context.Canceled`
   «штрафует» зависимость за то, что ушёл наш клиент.
7. **Пробный вызов толпой в half-open** — без эксклюзивности пробного
   вызова half-open = full load; защита исчезает ровно тогда, когда нужна.
8. **Порог breaker = 1** — цепь рвётся на первом же сетевом чихе;
   breaker становится источником отказов, а не защитой.
9. **Медленный вызов хуже быстрого отказа**: retry лечит отказ, но не
   медленность — для неё дедлайн и breaker; следите за латентностью, а
   не только за ошибками.
10. **`time.Sleep` вместо select с ctx** — отмена клиента не прерывает
    паузу; задержки складываются в хвост задержек всего сервиса.
