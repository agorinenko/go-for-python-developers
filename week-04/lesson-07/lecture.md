## Data race против race condition

Это разные вещи, и путать их опасно:

```go
// data race: два потока пишут/читают ОДНУ ячейку памяти без синхронизации
m := make(map[string]int)
go func() { m["a"] = 1 }()
m["b"] = 2 // гонка с горутиной: одновременный доступ к map — UB, часто фатально
```

```go
// race condition: логическая гонка «проверь-и-действуй» — код корректен по памяти,
// но результат зависит от переплетения операций
if balance >= price {  // проверка
    balance -= price   // действие — другой поток мог списать раньше
}
```

Гонку данных ловит race detector (и она — всегда баг). Логическую гонку
детектор не видит: её ловят только тесты инвариантов и дизайн (например,
атомарное «списать» одной операцией — `atomic.AddInt64` с проверкой).

## Race detector: что он ловит и сколько стоит

`go test -race`, `go build -race`, `go run -race` — включают
instrumented-среда выполнения (технология ThreadSanitizer). Детектор перехватывает
каждый доступ к памяти и строит граф «кто что читал/писал»; при двух
конфликтующих доступах без happens-before — сообщение с обоими стеками:

```
WARNING: DATA RACE
Write at 0x00c00012c1a0 by goroutine 7: main.main.func1()
Previous write at 0x00c00012c1a0 by main goroutine: main.main()
```

Цена: ~2× памяти и 10–20% CPU. Это не «тестовый» режим, а **обязательный**
этап CI для любого кода с конкурентностью; продакшен-исполняемый файл собирают без
`-race` (кроме случаев, когда инциденты дороже).

Ограничения:

1. Ловит только **выполнившиеся** переплетения: тест, не нагрузивший ветку
   конкурентно, гонку не увидит. Отсюда требование «конкурентные тесты — с
   реальной нагрузкой» (100 горутин в практике урока 7).
2. Не видит логических гонок (выше).
3. Не заменяет ревью: `-race` зелёный ≠ код правильный.

## Mutex и RWMutex

```go
var (
    mu    sync.Mutex      // эксклюзивная блокировка
    cache map[string]*Order
)

func put(id string, o *Order) {
    mu.Lock()
    defer mu.Unlock()     // Unlock при любом выходе, включая panic
    cache[id] = o
}
```

`defer mu.Unlock()` — норма: при панике мьютекс освободится, и процесс не
умрёт с «чужим» локаут-дедлоком. Держать мьютекс минимально долго (не
вызывать под ним сетевые операции).

**RWMutex** — когда чтений много, а записей мало: `RLock`/`RUnlock` —
совместное чтение, `Lock`/`Unlock` — эксклюзивная запись:

```go
func (c *Cache) Len() int {
    c.mu.RLock()
    defer c.mu.RUnlock()
    return len(c.data)
}
```

Выбор: чистые чтения — `RLock`; всё, что меняет состояние (включая LRU-порядок
в практике — `Get` двигает ключ!), — полный `Lock`. Не экономьте на
правильности: «немного изменил под RLock» — гонка. Важно: `RWMutex` не
дешевле Mutex на ровном месте (он сложнее внутри); его выгода — только в
сценарии «много читателей, редкий писатель».

## WaitGroup, atomic, Once

`sync.WaitGroup` (урок 5) — ожидание группы горутин: `Add` до старта, `defer
Done()`, `Wait` в конце.

**atomic** — неблокирующие операции над целыми и указателями:

```go
var hits atomic.Int64      // типизированные атомики Go 1.19+
hits.Add(1)
n := hits.Load()
hits.CompareAndSwap(old, new) // CAS — основа lock-free структур
```

Когда атомик уместен: счётчики, флаги, «одна ячейка». Когда нет: защита
**группы** полей — там нужен мьютекс, потому что атомарность каждой ячейки
не даёт атомарности набора (`играет ложно`-момент: счётчик+карта, обновлённые
порознь, видны в неконсистентной паре).

**sync.Once** — ровно однократное выполнение (ленивые синглтоны, отложенная
инициализация):

```go
var (
    once sync.Once
    client *catalogClient
)
func getClient() *catalogClient {
    once.Do(func() { client = dialCatalog() })
    return client
}
```

## sync.Map: когда она не нужна

`sync.Map` — не «потокобезопасный map на все случаи». Внутри — две карты
(read + dirty) с ленивым продвижением; она быстрее `map+mutex` только в
специфических сценариях: много разных ключей, редкие записи, **стабильное
множество ключей** (read-карта почти всегда попадает без блокировки), или
совместное владение ключами разными горутинами без общих мутаций. В
типичном кэше (`Put/Get/Delete` перемешаны, ключи меняются) `sync.Map`
**медленнее и тяжелее**, чем `map + RWMutex`. Правило: обычный
`map[string]T` под мьютексом, `sync.Map` — по профилю нагрузки, не по моде.

## errgroup: параллельные задачи с ошибками

`golang.org/x/sync/errgroup` — WaitGroup + сбор первой ошибки + отмена по
контексту:

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8) // semaphore из коробки
for _, item := range items {
    item := item
    g.Go(func() error {           // первая ошибка отменяет ctx остальных
        return validate(ctx, item)
    })
}
if err := g.Wait(); err != nil { // все дожданы, ошибка агрегирована
    return fmt.Errorf("validate: %w", err)
}
```

Это стандарт для «распараллелить N независимых операций и не потерять
ошибки»: вручную собирать ошибки из исполнителей — велосипед. В stdlib его нет
(пакет `golang.org/x/sync`), поэтому в практиках курса мы держимся stdlib;
в итоговом проекте с недели 7 errgroup появляется законно.

## Модель памяти: happens-before на уровне интуиции

Правил много ([полный текст](https://go.dev/ref/mem)), интуиции — три:

1. **Unlock → Lock.** Всё, что записано до `mu.Unlock()`, видно после
   `mu.Lock()` тем же мьютексом. Отсюда: «общие данные живут под мьютексом» —
   и всё.
2. **Завершение горутины → Wait.** `wg.Done()` делает видимым всё, что
   горутина писала, для `wg.Wait()`.
3. **Закрытие/отправка канала → приём.** Приём значения из канала видит всё,
   что отправитель сделал до отправки (канал — ещё и барьер памяти).

Если два доступа к памяти **не связаны** happens-before ни через одно из
правил — это гонка, даже если «на практике работает». В Go нет `volatile`:
вместо «пометить поле волатильным» вы выражаете порядок через примитивы
синхронизации — и это ровно то, что проверяет race detector.

## Go vs Python: GIL и логические гонки

```python
# Python: GIL сериализует байткод — «гонки памяти» на уровне CPython нет,
# но логическая гонка остаётся
count = 0
def inc():
    global count
    for _ in range(100_000):
        count += 1          # += — не атомарна логически: read-modify-write

threads = [threading.Thread(target=inc) for _ in range(4)]
[t.start() for t in threads]; [t.join() for t in threads]
print(count)                # почти наверняка < 400_000 — логическая гонка
```

```go
// Go: та же логическая гонка лечится атомарностью операции
var count atomic.Int64
var wg sync.WaitGroup
for range 4 {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for range 100_000 {
            count.Add(1)    // атомарный RMW — результат ровно 400_000
        }
    }()
}
wg.Wait()
```

Три вывода:

1. GIL делает CPython «безопасным по памяти» (нет segfault от гонок), но
   **не избавляет от логических гонок** — `count += 1` под потоками теряет
   инкременты ровно как в Go с обычной переменной. `threading.Lock` в Python
   — аналог `sync.Mutex`.
2. GIL не даёт потокам CPython CPU-параллелизма: 4 потока счёта работают как
   1. Горутины Go реально параллельны — и потому гонки в Go **фатальны**,
   а не «тихо теряют инкремент»: конкурентная запись в map падает с фатальной
   ошибкой среды выполнения.
3. В Go гонка — ловимая машиной ошибка (`-race`), в Python — незаметный
   логический дефект, который приходится вылавливать тестами вручную.

**C#:** `lock (obj) {}` ↔ `mutex.Lock/defer Unlock`; `ConcurrentDictionary`
↔ «map под мьютексом» (и не берите его «на всякий случай» по тем же
причинам, что `sync.Map`); `Interlocked.Add` ↔ `atomic.AddInt64`;
`Lazy<T>` ↔ `sync.Once`.

## Подводные камни и анти-паттерны

1. **Копирование мьютекса.** `Cache` по значению после первого `Lock` —
   скопированный мьютекс в новом состоянии; `go vet` ловит (`copylocks`), но
   лучше: структуры с мьютексом — всегда по указателю.
2. **Рекурсивный Lock** — `sync.Mutex` не реентерабелен: повторный `Lock`
   той же горутиной — deadlock. Если кажется, что нужен реентерабельный
   мьютекс, — перепроектируйте код.
3. **Чтение под Lock, запись под RLock** — гонка с фатальным исходом на
   map. LRU-`Get`, меняющий порядок, — это запись (см. практику).
4. **Забытый Unlock на раннем return** — лечится только `defer`.
5. **Атомики для группы полей** — «каждое поле атомарно, но вместе —
   неконсистентно»; нужен мьютекс.
6. **`sync.Map` по умолчанию** — медленнее `map+mux` в общем случае;
   выбирайте по профилю.
7. **WaitGroup: Add в горутине, Done без Add, повторное использование
   счётчика до Wait** — всё это паники или пропущенные ожидания.
8. **`-race` только в проде CI** — гонки должны падать тесты на каждом
   пуше, а не раз в неделю; конкурентные тесты — с реальной нагрузкой.
