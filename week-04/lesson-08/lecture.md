# Урок 8. context: отмена и дедлайны

## Цели урока

- понять context.Context как дерево отмены и дедлайнов;
- освоить WithCancel/WithTimeout/WithDeadline/WithValue и правила их
  применения;
- научиться строить причинно-следственную отмену: отмена родителя гасит детей;
- увидеть, как ctx отменяет HTTP-запросы и запросы к БД;
- сопоставить с asyncio.Task.cancel, asyncio.timeout и TaskGroup.

## Задача из капстоуна

Сервисный слой уже принимает `ctx` во всех методах (контракт недели 2), но
пока контекст сквозь них просто «проезжает». На этом уроке контекст
становится рабочим: таймауты на операции, мгновенная остановка при отмене
запроса, никаких «осиротевших» горутин. Практика — пакет `worker`: очередь
заданий, где у каждого задания свой таймаут, а отмена родителя мгновенно
останавливает обработку.

## context.Context: дерево отмены

`context.Context` — значение, которое несёт **сигнал отмены**, дедлайн и
несколько значений. Контексты образуют дерево: каждый производный контекст —
ребёнок родителя.

```go
ctx := context.Background()                  // корень без отмены и дедлайна
ctx, cancel := context.WithCancel(ctx)       // ручная отмена
ctx, cancel := context.WithTimeout(ctx, 5*time.Second) // дедлайн = now+5s
ctx, cancel := context.WithDeadline(ctx, time.Now().Add(time.Minute))
ctx := context.WithValue(ctx, key, val)      // данные, не управление
```

**Причинно-следственная отмена** — главное свойство: `cancel()` (или истёкший
дедлайн) родителя немедленно закрывает `Done()` **всех** детей, до любого
уровня вложенности. Поэтому контекст и передают **сквозь всю цепочку
вызовов**: HTTP-запрос → хендлер → сервис → репозиторий → SQL-запрос. Обрыв
соединения наверху гасит всю цепочку внизу — одной операцией, без явных
проводов.

`Done()` — канал, закрывающийся при отмене; `Err()` — причина: nil (жив),
`context.Canceled` (явная отмена), `context.DeadlineExceeded` (дедлайн).

```go
func work(ctx context.Context) error {
    select {
    case <-ctx.Done():
        return ctx.Err() // причина: Canceled или DeadlineExceeded
    case result := <-compute():
        return nil
    }
}
```

## Правила (часть ревью в любой Go-команде)

1. **ctx — первый аргумент** функции: `func (s *Service) GetOrder(ctx context.Context, id string) ...`.
2. **Не хранить ctx в структуре.** Контекст — про один запрос/операцию;
   поле структуры намекает, что структура живёт дольше операции. Исключение —
   структуры, которые и есть «владение» операцией (редко, осознанно).
3. **Никогда не передавать nil.** Нет контекста — `context.Background()`
   (корень приложения) или `context.TODO()` (маркер «ещё не решили»). Оба —
   «пустые», но честные.
4. **Один контекст на запрос, а не на приложение.** `Background` — для main
   и инициализации; всё, что связано с запросом, — производное от
   `r.Context()`.
5. **Проверять ctx.Err() активно** в циклах и долгих операциях: передать ctx
   дальше недостаточно, если код сам его игнорирует.

## WithTimeout: дедлайн и утечка таймера

```go
ctx, cancel := context.WithTimeout(parent, 100*time.Millisecond)
defer cancel() // НЕ забывать: иначе таймер живёт до дедлайна зря
```

`cancel` — не только «отменить раньше», но и **освободить ресурсы**: пока
контекст жив, рантайм держит таймер. `defer cancel()` в той же функции, где
контекст создан, — стандарт; `go vet` проверяет это за вас (анализатор
`lostcancel`: «the cancel function ... should be called, not discarded»).

Если cancel «некуда вернуть» (например, фабрика отдаёт только контекст),
таймер освобождают привязкой к родителю: `context.AfterFunc(parent, cancel)`
— cancel вызовется, когда родитель завершится, а сам ребёнок в любом случае
умрёт по своему дедлайну. Это ровно тот случай, который вы встретите в
практике урока.

Дедлайны не продлеваются: `WithTimeout(ctx, 5s)` на родителе с дедлайном
через 1с даст ребёнка с дедлайном через 1с. Проверка — `ctx.Deadline()`
(возвращает `(time.Time, bool)`).

## Отмена HTTP-запросов и запросов к БД

Вся stdlib и экосистема принимают ctx — и это свойство, а не случайность:

```go
// HTTP-сервер: контекст умирает вместе с соединением клиента
func handler(w http.ResponseWriter, r *http.Request) {
    order, err := svc.GetOrder(r.Context(), id) // клиент отвалился — цепочка погасла
    ...
}

// HTTP-клиент: таймаут на весь запрос
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
resp, err := http.DefaultClient.Do(req) // отмена прерывает и TLS, и чтение тела

// БД: таймаут на запрос, отмена транзакции
rows, err := pool.Query(ctx, `SELECT ...`) // pgx: ctx прерывает ожидание в пуле
tx, _ := pool.Begin(ctx)
defer tx.Rollback(ctx) // отмена ctx откатывает транзакцию
```

Серверные таймауты выставляются и на уровне сервера
(`http.Server.ReadTimeout`, `http.TimeoutHandler` для per-request), но
сетевые библиотеки лишь **распространяют** вашу отмену — принять решение
«сколько ждать» должен слой, который понимает бизнес (неделя 5, 11).

## WithValue: только request-scoped данные

`WithValue` кладёт значение в контекст под ключом. Правила жёсткие:

- только данные, **проходящие сквозь все слои** одного запроса: request ID,
  аутентифицированный пользователь, трейс-контекст;
- ключ — **приватный тип**, а не строка (строки коллизируют между пакетами):

```go
type ctxKey struct{} // приватный тип: другой пакет не подделает ключ

func WithUser(ctx context.Context, u User) context.Context {
    return context.WithValue(ctx, ctxKey{}, u)
}
func UserFrom(ctx context.Context) (User, bool) {
    u, ok := ctx.Value(ctxKey{}).(User)
    return u, ok
}
```

**Анти-паттерн:** обязательные параметры через контекст. `CreateOrder(ctx,
customerID, items)` — правильно; `CreateOrder(ctx)` c customerID в ctx —
нет: сигнатура лжёт, компилятор не проверяет, тесты ломаются молча. Значение
в ctx не должно быть **необходимым** для работы функции — только
дополнительным.

## Утечки горутин при отмене

Отмена работает, только если **все звенья цепочки её уважают**:

```go
// ПЛОХО: работа не проверяет ctx — отмена ни на что не влияет
go func() {
    time.Sleep(10 * time.Second) // после cancel горутина спит ещё 10 секунд
    save(order)
}()

// ХОРОШО: работа прерывается вместе с контекстом
select {
case <-time.After(10 * time.Second):
    save(order)
case <-ctx.Done():
    return // вышли сразу, ресурс не держим
}
```

Каждая горутина, которую вы запускаете, обязана либо завершиться сама, либо
слушать `ctx.Done()`. Иначе «быстрая отмена» превращается в медленную утечку
(сколько запросов отменилось — столько горутин висит). Практика урока
проверяет это счётчиком `runtime.NumGoroutine()`: после отмены хвостов не
остаётся.

## Go vs Python: asyncio.Task.cancel, asyncio.timeout, TaskGroup

```python
async def main():
    try:
        async with asyncio.timeout(5):            # Python 3.11+: дедлайн как контекст
            await fetch()
    except TimeoutError:
        ...

    async with asyncio.TaskGroup() as tg:         # структурированная отмена
        tg.create_task(worker(1))
        tg.create_task(worker(2))
    # ошибка одной задачи отменяет остальные, исключения собираются
```

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()
if err := fetch(ctx); err != nil {
    if errors.Is(err, context.DeadlineExceeded) { /* таймаут */ }
}
```

Сходства: `asyncio.timeout` ↔ `WithTimeout`; `TaskGroup`-отмена при ошибке ↔
`errgroup.WithContext` (урок 7); `Task.cancel()` бросает `CancelledError` в
точке `await` ↔ `ctx.Done()` закрывается в точке `select`.

Принципиальные отличия:

1. **Механизм доставки.** В Python отмена — исключение, влетающее в корутину
   (его надо ловить везде, где есть `await`). В Go отмена — закрытие канала:
   код проверяет её там, где ждёт (`select`), и не получает исключений.
2. **Явность передачи.** В Python контекст таймаута/задачи — часть
   фреймворка и области видимости; в Go ctx — **обычный аргумент**, его путь
   виден в сигнатурах и ревьюится.
3. **Протекание в синхронный код.** В Python отмена работает только в
   корутинах; синхронная функция (или сторонняя библиотека, зовущая
   блокирующий I/O) отмену не увидит. В Go ctx доходит до любого кода — от
   SQL-драйвера до кастомного цикла, лишь бы он проверял `ctx.Done()`.
4. **Дедлайны иерархичны** в Go: `WithTimeout(parent, ...)` знает про
   дедлайн родителя и берёт более ранний; в asyncio таймауты — контекстные
   менеджеры, и вложенность комбинируется вручную.

**C#:** `CancellationTokenSource` + `CancellationToken` — семантически самый
близкий аналог ctx (вплоть до `CancellationToken.None` ↔ `Background()` и
`CancellationTokenSource.CancelAfter` ↔ `WithTimeout`); правила «не хранить
токен в структуре, прокидывать аргументом» совпадают почти дословно.

## Подводные камни и анти-паттерны

1. **Забытый `cancel()`** — таймер контекста живёт до дедлайна впустую;
   `go vet` (lostcancel) — обязательный страж, `defer cancel()` — норма.
2. **ctx в структуре** — структура начинает нести чужой жизненный цикл;
   переиспользование сервиса с мёртвым контекстом — классический инцидент.
3. **`context.Background()` внутри обработчика запроса** — обрыв цепочки:
   отмена клиента перестаёт доходить до кода ниже. Внутри сервиса всегда
   работайте от пришедшего ctx.
4. **nil-контекст** (`func f(ctx context.Context)` с nil-аргументом) —
   паника при первом `ctx.Done()`; линтеры это ловят, привычка — тоже.
5. **WithValue для обязательных параметров** — невидимая сигнатура, тесты
   без проверок, рефакторинги вслепую.
6. **Ключ-строка в WithValue** — коллизия с другим пакетом и чужие данные
   под вашим ключом. Только приватные типы.
7. **Горутины, игнорирующие ctx** — «отмена» есть, а эффекта нет; каждая
   горутина обязана слушать `ctx.Done()` (или быть заведомо короткоживущей).
8. **Проверять `err == context.Canceled` вместо `errors.Is`** — обёртки
   сломают сравнение; `ctx.Err()` на стороне причины — это ещё не вся
   цепочка ошибок.

## Что делаем в капстоуне

1. В `internal/service` — ранняя проверка `ctx.Err()` в каждом публичном
   методе: сервис не работает с уже отменённым запросом.
2. В `internal/cache` (урок 7) — методы принимают `ctx` первым аргументом и
   проверяют его.
3. В `cmd/orders` — `context.WithTimeout` на стартовую инициализацию
   (прогрев кэша): зависшая инициализация не блокирует запуск навсегда.
4. С недели 5 каждый хендлер получает `r.Context()` — цепочка отмены
   «клиент → сервис → БД» замыкается.
