# Урок 2. Значения, nil и ошибки: чем Go принципиально отличается от Python

## Цели урока

- понять value semantics: копирование структур, указатели, разницу `new` и `make`;
- освоить `nil` и его ловушки (типизированный nil в интерфейсе);
- перейти от исключений к ошибкам-значениям: sentinel, `errors.Is/As`, оборачивание через `%w`;
- заложить доменную модель итогового проекта.

## Задача из итогового проекта

Сервис заказов начинается с доменной модели: `Order`, `OrderItem`, статусы

модели заморожен в [CAPSTONE.md](../../CAPSTONE.md) — все следующие недели
опираются на него.

## Значения, копирование, указатели

В Go **присваивание копирует структуру целиком**:

```go
o1 := Order{ID: "o-1", Total: 100}
o2 := o1        // полная копия
o2.Total = 200  // o1.Total остался 100
```

Это value semantics — как `struct` в C#, и в отличие от Python, где `o2 = o1`
даёт вторую ссылку на тот же объект (`o2.total = 200` изменит и `o1`).

Указатель — явный и видимый:

```go
o := &Order{}   // указатель на структуру
o.Total = 100   // Go сам разыменовывает: то же, что (*o).Total
```

Когда нужен указатель?

- структура большая, и её часто копируют (например, передают в функции);
- нужно, чтобы изменения были видны вызывающему;
- поле-опция (`*string` против `string` — nil означает «не задано», в отличие от
  «пустая строка»).

Go сам решает, класть переменную на стек или в кучу (escape analysis, подробно
на неделе 9). Синтаксис не подсказывает: `o := &Order{}` может жить и на стеке.

**`new` и `make` — разное.** `new(T)` возвращает `*T` с zero value (почти не
используется — пишут `&T{}`). `make` — только для slice/map/channel, которые
нуждаются в инициализации внутренностей.

## Ссылочные типы и nil

Слайсы, карты, каналы, интерфейсы, функции, указатели — ссылочные: присваивание
копирует «заголовок», а не данные.

```go
a := []int{1, 2}
b := a          // общий подлежащий массив!
b[0] = 99       // a[0] тоже стал 99
```

Для слайса, карты и канала zero value — `nil`:

```go
var m map[string]int // nil-карта
m["x"] = 1           // panic: assignment to entry in nil map
var s []int          // nil-слайс
s = append(s, 1)     // ок: append создаёт массив
```

**nil-слайс и пустой слайс — разные вещи**, и это видно в JSON: `nil` →
`null`, `make([]T, 0)` → `[]`. Для API-контрактов это важно (неделя 5).

Строки в Go неизменяемы (как в Python), но это байтовые последовательности:
`len("Привет") == 12` (байты в UTF-8!), а количество символов — через
`utf8.RuneCountInString`. Итерация `for i, ch := range s` идёт по рунам, поэтому
`i` прыгает на 2 для кириллицы.

## Zero values: «nil, где можно, ноль, где нельзя»

У каждого типа есть zero value, переменные всегда инициализированы:

| Тип | Zero value |
|---|---|
| `int`, `float64` | `0` |
| `string` | `""` (не null!) |
| `bool` | `false` |
| `*T`, `slice`, `map`, `chan`, `func`, `interface` | `nil` |
| `struct` | все поля по zero value |

В Python аналог — только через `None` и ручную инициализацию в `__init__`.
В Go zero value избавляет от «uninitialized variable» целиком — недоинициализация
невозможна на уровне языка.

## Типизированный nil: главная ловушка

Интерфейс — это пара `(тип, значение)`. Интерфейс **не равен nil**, если тип в
нём не nil:

```go
var r *Repository = nil // конкретный nil-указатель
var repo IRepository = r
fmt.Println(repo == nil) // false!
```

Внутри `repo` лежит пара `(*Repository, nil)`. Интерфейс равен nil только если
и тип, и значение nil. Классическая ошибка: функция возвращает интерфейс, а
внутри — nil-указатель конкретного типа; вызывающий проверяет `if err == nil`
и падает с nil pointer dereference позже. Правило: **возвращайте из функций
конкретные типы; интерфейсы — только если это осознанно**. Детально — на
уроке 3.

## Ошибки: значения вместо исключений

В Go нет исключений. Функция возвращает ошибку как обычное значение:

```go
func Save(o *Order) error { ... }

if err := Save(o); err != nil {
    return fmt.Errorf("save order %s: %w", o.ID, err)
}
```

Четыре инструмента, которые покрывают 95% потребностей:

```go
// 1. Sentinel-ошибки — «проверь по ссылке»:
var ErrOrderNotFound = errors.New("orders: order not found")
if errors.Is(err, ErrOrderNotFound) { ... } // проходит и через обёртки

// 2. Оборачивание с контекстом:
return fmt.Errorf("get order %s: %w", id, err) // %w — сохранить цепочку

// 3. Типизированные ошибки — «достань по типу»:
var nfErr *NotFoundError
if errors.As(err, &nfErr) { ... } // достаёт из цепочки

// 4. Объединение нескольких ошибок:
return errors.Join(err1, err2) // Go 1.20+
```

Соглашения (жёсткие, часть ревью):

- текст ошибки — **строчными, без точки в конце**, по-английски: `"open file"`,
  не `"Open file."`;
- не начинать с `error`/`failed` — префикс `failed to` избыточен;
- оборачивать всегда, когда поднимаетесь по слоям: каждый слой добавляет контекст;
- **не сравнивать** `err.Error()` строкой — только `errors.Is`/`As`;
- не заводить ошибку, если её никто не обрабатывает особым образом.

**Panic — не механизм ошибок.** Паника — для невосстановимых состояний
(инвариант нарушен, программист ошибся) и `index out of range`-подобных
ситуаций. Восстановление через `recover` — только на границе сервиса
(week 5, middleware), как `except BaseException` в самом внешнем слое.

**Python:** исключения — основной канал ошибок, и тип исключения несёт
семантику (`except KeyError`). В Go семантика — в значении: `errors.Is` играет
роль `except KeyError`, `errors.As` — `except ValueError as e: e.field`.
Обёртывание `%w` — аналог `raise ... from err` в Python 3. Плюс Go: цепочку
ошибок видно целиком, ошибка — обычные данные, их можно агрегировать
(`errors.Join`). Минус: «шум» `if err != nil` — но это цена явности.

## Go vs Python: сдвиг мышления

```python
# Python: LBYL/EAFP + исключения
order = repo.get(order_id)              # KeyError/OrderNotFoundError
if order.status != "new":               # типов нет — опечатка в "new" пройдёт
    raise InvalidTransition(...)
```

```go
// Go: ошибка — значение, состояния — типы
o, err := repo.GetByID(ctx, id)         // err != nil — обычная ветка
if err != nil {
    return nil, fmt.Errorf("get order %s: %w", id, err)
}
if err := o.ApplyStatus(domain.StatusPaid); err != nil { // "paid" не скомпилируется с опечаткой
    return nil, err
}
```

Два следствия:

1. **Нельзя «забыть» обработать ошибку** — но можно её молча проглотить.
   Линтер `errcheck` и ревью следят за этим.
2. **Состояния моделируйте типами**: статус заказа — это `OrderStatus`, а не
   строка, «не задано» — `*string`/`nil`, а не магическая `""`. Опечатки
   отлавливает компилятор, а не продакшен.

Структуры против dataclass: `OrderItem` — это `@dataclass(frozen=True)` без
методов-мутаторов и без наследования; валидацию в `__post_init__` заменяют
конструкторы-фабрики (`NewOrder`) и методы-проверки.

## Подводные камни

1. **Запись в nil-карту — panic.** Инициализируйте карты через `make`/литерал;
   для конкурентного доступа — `sync.Map` или мьютекс (урок 7).
2. **Aliasing слайсов.** `b := a[:2]` и `b := append(a, x)` могут делить
   подлежащий массив с `a` — «призрачные» изменения. Копия — `slices.Clone`
   (Go 1.21+).
3. **Типизированный nil** (см. выше) — тестируйте ветку ошибок на nil.
4. **Shadowing ошибки**:

   ```go
   if err := step1(); err != nil { return err }
   if err := step2(); err != nil { /* err — уже не та переменная! */ }
   ```

   Во втором `if` проверяется err от `step1`. Лечится разными именами или
   `=` вместо `:=` в одной области видимости. `go vet` ловит частный случай.
5. **Сравнение ошибок через `==`** вместо `errors.Is` — ломается при первом же
   `%w` в цепочке.
6. **Деньги в float64** — `0.1 + 0.2`. В итоговом проекте цены — `int64` копеек.
7. **`time.Now()` в конструкторе** — тесты не смогут подменить время.
   Передавайте часы или метку явно, когда время важно.
