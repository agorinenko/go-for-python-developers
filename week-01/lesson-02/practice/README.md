# Практика. Урок 2: доменная модель заказа

Пакет `orders` — сердце капстоуна. Контракт (типы, статусы, переходы)
заморожен в [CAPSTONE.md](../../../CAPSTONE.md), раздел «Неделя 1»: менять
сигнатуры и имена экспортируемых элементов нельзя — на них опираются все
последующие недели.

## Задание

Реализуйте `TODO` в `orders/order.go`:

1. `NewOrder` — фабрика: валидация аргументов, расчёт `Total`, `CreatedAt`.
2. `Validate` — повторная проверка инвариантов заказа.
3. `RecalcTotal` — пересчёт суммы по позициям.
4. `ApplyStatus` — машина переходов.

Требования к ошибкам (лекция, раздел «Ошибки»):

- sentinel-ошибки уже объявлены, используйте `errors.Is`-совместимые обёртки;
- ошибку позиции оборачивайте в `ErrInvalidItem` **с деталями** — по сообщению
  должно быть понятно, какая позиция и почему невалидна: `fmt.Errorf("%w: product %q: quantity must be > 0", ErrInvalidItem, item.ProductID)`;
- невалидный переход — `ErrInvalidTransition` с указанием обоих статусов.

Допустимые переходы: `new → validated → paid`, `new → cancelled`.

## Критерий сдачи

```sh
go mod tidy
go vet ./...
go test ./...
```

Всё зелёное.

## Перенос в капстоун

Скопируйте `orders/order.go` и `orders/order_test.go` в `orders/internal/domain/`
капстоуна, переименуйте пакет в `domain` (включая импорты в тестах — теперь это
`orders/internal/domain`), и добейтесь `go test ./...` внутри капстоуна.
С этого момента `internal/domain` — каноническая модель проекта.
