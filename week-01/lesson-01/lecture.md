# Урок 1. Инструментарий и структура проекта Go

## Цели урока

- собрать, запустить и протестировать программу на Go; понять модель модулей и зависимостей;
- настроить цепочку качества: `gofmt`, `go vet`, `golangci-lint`, `Makefile`;
- выбрать структуру проекта под микросервис;
- увидеть, чем экосистема Go принципиально отличается от Python, C# и JS.

## Задача из итогового проекта

Весь курс мы строим микросервис заказов (`orders`). На этом уроке закладывается
фундамент: модуль, раскладка каталогов, сценарии сборки и проверок. Опытный
разработчик знает, что цена плохой раскладки и отсутствующего линтера — это недели
рефакторинга на старте продакшена, поэтому мы начинаем не с «Hello, World», а с
инструментов, которыми этот проект будет проверяться все 12 недель.

## Набор инструментов одним экраном

У Go нет виртуальных окружений, нет runtime для установки на сервер, нет пакетного
менеджера в привычном смысле. Есть один исполняемый файл `go`:

| Команда | Что делает | Аналог в Python |
|---|---|---|
| `go build ./...` | компилирует пакеты (артефакт — статический исполняемый файл) | — |
| `go run .` | собирает и запускает | `python app.py` |
| `go test ./...` | запускает тесты | `pytest` |
| `go vet ./...` | статический анализ подозрительного кода | `ruff`/`mypy` (частично) |
| `go fmt` | форматирует код | `black` |
| `go mod tidy` | синхронизирует `go.mod`/`go.sum` с кодом | `uv sync`/`poetry lock` |
| `go get pkg@v1.2.3` | добавляет/обновляет зависимость | `pip install` + правка файла |
| `go install path@latest` | ставит **программу** (CLI) | `pipx install` |
| `go doc net/http` | документация пакета/символа | `help()`/pydoc |

`./...` — рекурсивное «все пакеты начиная отсюда». Это самый часто используемый
аргумент в Go-проектах, привыкайте сразу.

Полезные переменные окружения:

- `GOPROXY` — прокси модулей, по умолчанию `https://proxy.golang.org` (кеш всего
  публичного кода);
- `GOPRIVATE`, `GONOSUMDB`, `GONOSUMCHECK` — обход прокси/checksum-базы для
  приватных репозиториев корпораций;
- `CGO_ENABLED=0` — собрать без cgo (чистый статический исполняемый файл, важно для Docker);
- `GOOS`/`GOARCH` — кросс-компиляция: `GOOS=linux GOARCH=arm64 go build` соберёт
  исполняемый файл под Linux ARM прямо с Mac.

Кросс-компиляция «из коробки» — свойство, которое Python-проекты получают только
ценой Docker и wheel-инфраструктуры. В Go один и тот же исполняемый файл уходит на любой
Linux-хост без интерпретатора, без venv, без установленных пакетов.

## Модули: go.mod, зависимости и версии

Каждый проект — **модуль**: каталог с `go.mod`:

```
module orders

go 1.25

require (
    github.com/go-chi/chi/v5 v5.2.3
    github.com/jackc/pgx/v5 v5.7.6
)

require ( /* indirect-зависимости */ )
```

- `go mod init orders` — создать модуль.
- Версии используют семантическое версионирование (SemVer) — формат `MAJOR.MINOR.PATCH`,
  где MAJOR ломает совместимость, MINOR добавляет возможности, PATCH только исправляет
  ошибки. Go выбирает версии алгоритмом **MVS** (Minimal Version Selection): для
  каждого модуля берётся **наименьшая версия, удовлетворяющая всем требованиям сразу**,
  а не самая свежая из опубликованных. Если два пакета требуют v1.2.0 и v1.3.0,
  возьмётся v1.3.0 — это максимум из запрошенных минимумов; версия v1.9.0, даже если
  она уже вышла, взята не будет. Так сборки воспроизводимы без lock-файла в привычном
  смысле.
- `go.sum` — контрольные суммы использованных версий. **Коммитится в git
  всегда** (в отличие от `node_modules` или `dist`).
- `go mod tidy` — привести `go.mod`/`go.sum` в соответствие с импортами кода.
  Запускайте после каждого изменения зависимостей; CI обязан проверять, что tidy
  ничего не меняет.
- `replace` — подмена пути/версии (локальная разработка нескольких модулей);
  `vendor/` — замороженная копия зависимостей (редко нужна, в основном для
  оффлайн-сборок).
- Псевдо-версии `v0.0.0-20240101...-abc123` — так выглядит зависимость от
  конкретного коммита.

**Python:** `pip` ставит «последнюю совместимую», конфликты разрешаются в среде выполнения
(или на этапе `pip check`); lock-файлы появились только с Poetry/uv. **C#:** NuGet
резолвит граф пакетов похоже, но у Go нет централизованного «пакетного менеджера» —
зависимость это просто git-репозиторий.

## Структура проекта

Go не диктует layout, но сообщество выработало соглашения. Для сервиса подходит:

```
orders/
├── cmd/orders/          # один main на исполняемый файл; логики здесь почти нет
├── internal/            # код, недоступный другим модулям
│   ├── domain/          # модель предметной области
│   ├── service/         # бизнес-логика
│   ├── storage/         # реализации хранилищ
│   └── httpapi/         # транспортный слой
├── api/                 # контракты (proto, openapi)
├── deployments/         # docker, k8s, CI
└── Makefile
```

Ключевые правила:

1. **`internal/` — капсуляция на уровне компилятора.** Импортировать пакет из
   `internal/` может только код внутри того же поддерева модуля. Ваш транспортный
   слой физически не может обратиться к приватным деталям другого. Аналога в
   Python нет (там всё держится на договорённостях `_underscore`).
2. **`cmd/` — точка входа.** Один каталог на один исполняемый файл, `main` тонкий: прочитать
   конфиг, собрать зависимости, запустить сервер. Никакой бизнес-логики.
3. **Плоскость лучше вложенности.** В Go приняты маленькие пакеты с чёткими
   границами. Вложенные пакеты-«утилиты» (типа `utils/`, `common/`, `helpers/`) —
   анти-паттерн: такой пакет — магнит для свалки.
4. **Не тащите `pkg/` без причины.** Каталог `pkg/` — для кода, который
   осознанно публикуется наружу. Внутренний сервис обычно обходится без него.
5. github.com/golang-standards/project-layout — популярная раскладка, но это
   набор примеров, а не стандарт. Не стройте «layout ради layout».

**C#:** здесь вы привыкли к «решениям и проектам» — в Go один модуль может быть
сразу и «решением», и «проектом»; исполняемых файлов из одного модуля можно собрать несколько
(`cmd/orders`, `cmd/worker`).

## Качество кода: gofmt, go vet, линтеры

Стиль в Go — не предмет спора, а инструмент:

- **`gofmt`** — канонический форматер. Табы, единые отступы, порядок импортов.
  Форматирование `gofmt` — **единственно допустимое**. Никаких
  `black --line-length 120`, никаких споров про стиль: `gofmt` закрыл этот вопрос
  навсегда (аналогия: PEP 8, но enforced). В редакторах — format-on-save.
- **`go vet`** — статический анализ: подозрительные `fmt.Printf`, некорректные
  структурные тэги, небезопасные преобразования. Всегда зелёный.
- **`golangci-lint`** — металинтер, собирающий десятки линтеров. Разумный стартовый
  набор: `errcheck` (непроглоченные ошибки), `govet`, `staticcheck` (глубокий
  статический анализ), `ineffassign`, `unused`, `revive` (стиль, заменяет golint),
  `misspell`. Конфиг — `.golangci.yml` в корне, версия линтера закрепляется, чтобы
  CI не начал «краснеть» из-за обновления. Пример конфига для базового проекта
  (формат golangci-lint v2, проверен на v2.15):

  ```yaml
  version: "2"

  linters:
    default: none
    enable:
      - errcheck
      - govet
      - ineffassign
      - staticcheck
      - unused
      - revive
      - misspell
  ```

  Для старого golangci-lint v1 тот же смысл записывается иначе: без строки
  `version`, а вместо `default: none` — `disable-all: true`.

**Python:** связка `black` + `ruff` + `mypy` решает ту же задачу, но из нескольких
инструментов с настройкой. В Go одна команда `go vet` встроена, вторая
(`golangci-lint`) — индустриальный стандарт. **JS:** `eslint` + `prettier` — тот же
паттерн «линтер + форматер».

## Makefile как единая точка входа

Make — де-факто стандарт сценариев в Go-проектах (не только для сборки: миграции,
генерация кода, локальный запуск всего стека). Каркас для итогового проекта:

```makefile
BIN := orders

.PHONY: build run test vet fmt lint

build:
	go build -o bin/$(BIN) ./cmd/orders

run:
	go run ./cmd/orders

test:
	go test -race ./...

vet:
	go vet ./...

fmt:
	gofmt -w ./cmd ./internal

lint:
	golangci-lint run
```

Зачем, если есть `go build`? Затем, что новый разработчик (или вы через полгода)
не должен помнить флаги: `make test` всегда означает «тесты с race detector»,
`make lint` — «проверка перед пушем». Это контракт команды.

## Go vs Python: взгляд с высоты

| | Go | Python |
|---|---|---|
| Исполнение | AOT-компиляция в статический исполняемый файл | интерпретация (CPython) |
| Типизация | статическая, структурная | динамическая, «утки» |
| Артефакт развёртывания | один исполняемый файл | исходники + venv + пакеты |
| Конкурентность | goroutine + каналы (недели 3–4) | asyncio / threads, GIL |
| Форматирование | `gofmt`, без вариантов | `black` + соглашения |
| Проверки | `go vet` + golangci-lint | ruff + mypy |
| Зависимости | модули, MVS, `go.sum` | pip + lock (uv/poetry) |
| Обработка ошибок | значения, `if err != nil` | исключения |

Главный сдвиг мышления: в Python вы разворачиваете **сервис вместе со средой выполнения**
(интерпретатор, системные пакеты, venv); в Go вы собираете **самодостаточный
артефакт**. Конвейер развёртывания сокращается до «собрал — залил исполняемый файл — запустил».

## Подводные камни

1. **Старые статьи про GOPATH.** До модулей (Go ≤1.10) код жил в `$GOPATH/src`.
   Всё, что говорит «склонируй в GOPATH», устарело лет на восемь.
2. **`go get` для установки CLI.** `go get` управляет зависимостями **модуля**;
   ставить программы нужно `go install path@version`. Путаница — частый источник
   «у меня в go.mod мусор».
3. **`go.sum` выброшен из git.** Сборка сломается у всех, кроме автора (или
   включится сетевой фетч с риском подмены). `go.sum` коммитим всегда.
4. **Корпоративный прокси.** В закрытых сетях публичные модули идут через
   внутренний прокси: `GOPROXY=corp-proxy,proxy.golang.org,direct`, а приватные —
   `GOPRIVATE=github.com/mycorp/*`, иначе получите ошибки про неизвестную ревизию
   на внутренних репозиториях.
5. **Строка `toolchain` в go.mod.** При сборке старым Go проект с `go 1.25` может
   сам скачать нужную версию Go. В офлайн-CI это падает — либо синхронизируйте
   версию Go в CI с go.mod, либо `GOTOOLCHAIN=local`.
6. **Модуль против каталога.** Модуль — это каталог с `go.mod`, не обязательно
   корень репозитория. Вложенные модули (как практики этого курса — каждая со
   своим `go.mod`) Go-инструменты при обходе `./...` просто пропускают.

## Что делаем в итоговом проекте

1. Создаём `orders/`: `go mod init orders`, раскладка по контракту из
   [CAPSTONE.md](../../CAPSTONE.md).
2. Пишем `Makefile` с целями `build`, `run`, `test` (`-race`), `vet`, `fmt`,
   `lint`.
3. Создаём `.golangci.yml` с базовым набором линтеров.
4. Добиваемся: `make lint` и `make test` зелёные, `gofmt` ничего не меняет.
