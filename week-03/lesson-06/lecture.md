# Урок 6. Каналы и select

## Цели урока

- освоить семантику каналов: блокировка, буферы, закрытие, nil-канал, range;
- научиться `select`: default, таймауты, отмена, приоритеты;
- разобрать канонические паттерны: pipeline, fan-out/fan-in, worker pool,
  done-канал, сигнальный канал `struct{}`;
- понять, кто владеет каналом и кто его закрывает;
- сопоставить с `asyncio.Queue`, `asyncio.gather` и семафорами Python.

## Задача из капстоуна

Заказы проходят несколько стадий обработки: валидация позиций, пересчёт
итога, смена статуса. На прошлом уроке мы распараллелили один шаг; теперь —
собираем **конвейер**: первый этап параллельный (fan-out/fan-in), остальные
последовательные, всё — с отменой по контексту и пробросом ошибок. Это
практика урока: пакет `pipeline`.

## Каналы: три режима

Канал — типизированная очередь синхронизации:

```go
ch := make(chan Order)     // небуферизованный: рандеву
ch := make(chan Order, 10) // буферизованный: до 10 значений без блокировки
```

- **Небуферизованный канал** синхронизирует: отправка завершается, только
  когда принимающий уже готов принять. Это и передача данных, и
  рандеву-барьер одновременно.
- **Буферизованный** — очередь с ограничением: отправитель блокируется при
  переполнении. Буфер — это **backpressure**: быстрый производитель
  упирается в буфер и замедляется, а не топит память. Размер буфера — не
  «побольше», а расчётный допуск на пиковые колебания (урок 11 — подробно).

Приём:

```go
o, ok := <-ch   // ok == false — канал закрыт и опустошён
for o := range ch { ... } // читать до закрытия
```

Закрытие:

```go
close(ch)
```

Семантика закрытия несимметрична: **запись в закрытый канал — паника**;
**чтение из закрытого — немедленный zero value** с `ok == false`; повторное
закрытие — паника. Читатель не может отличить «канал закрыт» от «канал
пуст, но жив» без `ok`.

**nil-канал**: отправка и приём блокируются **навсегда**. В `select` ветка
nil-канала просто отключена — этим пользуются, чтобы динамически
включать/выключать ветки (например, «не принимать запросы, пока идёт
реконфигурация»).

## select: мультиплексирование

```go
select {
case o := <-orders:
    process(o)
case <-ctx.Done():          // отмена
    return ctx.Err()
case <-time.After(5 * time.Second): // таймаут
    return errTimeout
default:                    // неблокирующая проверка
}
```

Правила: выбирается **готовая** ветка; если готовых несколько — случайно
(справедливость); `default` делает select неблокирующим. Про таймауты —
важно: `time.After` аллоцирует таймер, который **не освобождается до
срабатывания** — в цикле с быстрыми операциями это утечка таймеров. В цикле:

```go
timer := time.NewTimer(5 * time.Second)
defer timer.Stop()
select {
case <-timer.C:
    ...
}
```

## Канонические паттерны

**Pipeline** — этапы, соединённые каналами: выход одного — вход другого.

```go
func stage(ctx context.Context, in <-chan Order, out chan<- Order) error {
    for o := range in {
        out <- enrich(o)
    }
    return nil
}
```

**Fan-out / fan-in** — один вход раздаётся N воркерам, выходы собираются:

```go
in := make(chan Order)
outs := make([]<-chan Order, n)
for i := 0; i < n; i++ {
    outs[i] = worker(ctx, in)     // каждый воркер — свой выходной канал
}
for o := range merge(outs...) {   // fan-in: объединить потоки
    handle(o)
}
```

Обычный fan-in теряет **порядок**: результаты приходят в порядке завершения
воркеров. Когда порядок важен (наш капстоун!), раздавайте заказы воркерам
**по кругу** (индекс `% N`) и собирайте по кругу же: `collected[0][k],
collected[1][k], ...` — так параллельная обработка выглядит снаружи
последовательной. Условие: воркер обязан сохранять порядок своего потока и
обрабатывать заказы 1:1.

**Worker pool** — N горутин читают общий канал заданий (урок 5): пул — это
fan-out без слияния (результаты — по индексам).

**Done-канал и сигнальный канал:**

```go
done := make(chan struct{})   // struct{} — 0 байт: только сигнал, без данных
go func() {
    doWork()
    close(done)               // закрытие — широковещательный сигнал ВСЕМ
}()

for _, w := range workers {
    <-done                    // каждый ждущий просыпается сразу
}
```

`close(done)` — идиоматический «event»: в отличие от отправки значения,
пробуждает всех ждущих, а не одного. **Or-done** — обёртка, превращающая
«канал + done» в чистый канал, удобный для `range`.

**Владелец канала.** Канал закрывает тот, кто в него пишет (владелец), —
никогда принимающий. Причина: отправитель в закрытый канал паникует; если
закрыть будет принимать сторона, отправитель не может знать, когда это
произойдёт. Единственный способ «сказать всем, что данных больше нет» —
закрыть канал в единственном месте, где его создали и наполняют.

**Backpressure через буферы** уже упомянута: `make(chan T, n)` — это
допуск на опережение продюсером консьюмера на n элементов.

## Отмена и ошибки в конвейере

Конвейер без отмены — утечка горутин: при ошибке середины конвейера
начальные этапы продолжают слать в канал, который никто не читает, и виснут
навсегда. Поэтому каждый этап принимает `ctx` и проверяет его в цикле, а
оркестратор (наш `Run`) должен:

- селектить на `ctx.Done()` и на сигнал ошибки при **раздаче** (иначе
  зависнет на отправке в канал уже вышедшего воркера);
- при ошибке любого воркера — останавливать раздачу, закрывать входные
  каналы, дать остальным воркерам штатно выйти;
- вычитывать выходы воркеров **параллельно** с их работой (иначе воркер
  заблокируется на отправке, и `Wait` никогда не завершится — классический
  deadlock).

Эти три пункта — ровно те грабли, на которых падает первый же «самодельный»
конвейер; практика урока заставляет их обойти.

## Go vs Python: asyncio.Queue и gather

```python
# asyncio: очередь + gather + семафор
q = asyncio.Queue(maxsize=10)
sem = asyncio.Semaphore(8)

async def worker():
    while True:
        order = await q.get()       # блокировка без блокировки event loop
        async with sem:
            await process(order)
        q.task_done()

tasks = [asyncio.create_task(worker()) for _ in range(8)]
await q.join()
```

```go
// Go: каналы — значения в языке, а не объекты библиотеки
jobs := make(chan Order, 10)
sem := make(chan struct{}, 8)
var wg sync.WaitGroup
for w := 0; w < 8; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for o := range jobs {
            sem <- struct{}{}
            process(o)
            <-sem
        }
    }()
}
for _, o := range orders {
    jobs <- o
}
close(jobs)
wg.Wait()
```

Сходства: `asyncio.Queue(maxsize)` — буферизованный канал с backpressure,
`asyncio.gather` — fan-in с сохранением порядка (порядок gather — порядок
переданных корутин, что удобнее, чем каналы), `Semaphore` — семафор из
урока 5. Отличия: в asyncio `await q.get()` — точка кооперативного
переключения, несущая ограничение «не вызывай блокирующее внутри»; в Go
блокировка на канале — просто блокировка горутины, планировщик сам
переключится. И главное: канал в Go — это **тип первого класса** (значение,
которое можно передавать, хранить, селектить), а не объект фреймворка —
поэтому паттерны pipeline/fan-out комбинируются произвольно, без
согласования с библиотекой.

**C#:** `Channel<T>` (System.Threading.Channels) — ближайший аналог
каналов с BoundedCapacity как буфером; `Task.WhenAll` ↔ gather/fan-in;
`Parallel.ForEachAsync` с MaxDegreeOfParallelism ↔ worker pool.

## Подводные камни и анти-паттерны

1. **Запись в закрытый канал** — паника, часто отсроченная: гонка «закрыли,
   пока отправитель ещё слал». Правило владельца канала убирает её
   структурно.
2. **Закрытие со стороны читателя** — тот же класс паники плюс
   неопределённость для отправителей. Приёмник сообщает о завершении через
   `done`-канал или `ctx`, а не через close.
3. **Горутина висит на отправке.** `ch <- x` в никем не читаемый канал —
   утечка (урок 5). Каждая отправка должна иметь либо потребителя, либо
   ветку отмены в `select`.
4. **`time.After` в цикле** — утечка таймеров (см. выше); в циклах —
   `time.NewTimer` + `Stop`.
5. **nil-канал по невниманию.** Забытый `make` — nil-канал: `select` молча
   пропускает ветку, а не паникует; баг проявляется как «иногда ничего не
   приходит».
6. **Deadlock из-за Wait до вычитки.** `wg.Wait()` до того, как выходные
   каналы воркеров начали читать, — вечная блокировка на отправке. Читатели
   должны работать параллельно воркерам.
7. **Буфер как «решение» проблемы.** Увеличение буфера вместо устранения
   медленного консьюмера откладывает переполнение, а не лечит его.
8. **Потеря порядка при fan-in** — там, где порядок входит в контракт
   (списки заказов!), используйте круговую раздачу/сбор или gather-подобную
   схему с индексами.

## Что делаем в капстоуне

Переносим `pipeline` в `orders/internal/service/pipeline.go`: тип `Order` —
из `domain`, этапы — `Stage` с контрактом 1:1 и порядком потока, `Run` —
fan-out первого этапа (N = GOMAXPROCS) с восстановлением порядка, отмена по
`ctx`, проброс ошибок. Применение: пакетная переоценка заказов
(`RecalcOrders`). Тесты — с `-race`.
