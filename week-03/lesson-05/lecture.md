# Урок 5. Горутины и планировщик

## Цели урока

- понять, почему goroutine дешевле потока и как растёт её стек;
- разобрать планировщик M:N: G/P/M, work stealing, GOMAXPROCS, преемпшн;
- научиться ограничивать конкурентность (семафор, worker pool);
- увидеть, как выглядят и как ловятся утечки горутин;
- сопоставить модель Go с asyncio (Python) и Task/ThreadPool (C#).

## Задача из капстоуна

`OrderService.CreateOrder` валидирует позиции последовательно. Каждая
позиция проверяется внешним валидатором (на неделе 7 он станет gRPC-вызовом
в сервис каталога — то есть сетевым, медленным). Значит, валидацию нужно
распараллелить — с ограничением конкурентности и строгим порядком
результатов. Это и делает практика урока.

## Goroutine: дешёвая сопрограмма

```go
go doWork()            // асинхронный запуск функции
```

Goroutine — не поток ОС. Это легковесная сопрограмма со **стартовым стеком
~2 КБ**, который растёт и сжимается по мере необходимости (копированием, как
`list` в CPython наоборот). Поток ОС стартует с 1–8 МБ фиксированного стека,
поэтому тысячи потоков — уже проблема, а сотни тысяч горутин на одном
процессе — нормальный продакшен:

```go
for i := 0; i < 100_000; i++ {
    go func(id int) { ... }(i)
}
```

Переключение между горутинами — это смена указателя стека в рантайме, без
syscall и без сброса TLB. Горутина блокируется, только когда блокируется её
системный вызов (или когда она сама ждёт на канале/мьютексе — но это тоже
управляется рантаймом, а не ядром).

## Планировщик M:N

Модель трёх букв:

- **G** — goroutine, единица пользовательского кода;
- **M** — machine, поток ОС;
- **P** — processor, «контекст исполнения» с локальной очередью готовых G.
  Число P = `GOMAXPROCS` (по умолчанию — число ядер).

M выполняет G, пока привязан к P. Свободные M «крадут» (work stealing)
половину очереди у занятого P, когда своя очередь пуста, — так балансируется
нагрузка без единого планировщика с глобальной блокировкой.

Два вида блокировок обрабатываются по-разному:

- **сетевая блокировка** (read на сокете) — горутина «паркуется» в netpoller,
  M освобождается и берёт следующую G: тысячи ожидающих HTTP-ответа горутин
  не занимают ни одного потока;
- **блокирующий syscall** (файловый I/O, cgo) — M уходит в ядро, рантайм
  поднимает резервный M, чтобы P не простаивал.

`runtime.GOMAXPROCS(n)` меняет число P в рантайме (или `GOMAXPROCS=n` в
окружении). Занижение полезно для бенчмарков и лимитов; завышение сверх ядер
обычно вредит.

## Преемптивная многозадачность

Современный планировщик Go **вытесняющий**: с Go 1.14 горутина, выполняющая
чистый CPU-цикл (`for { i++ }`), не заблокирует другие — сигнал преемпшна
прервёт её в безопасной точке. До этого планировщик был кооперативным:
переключение происходило только в точках вызова функций. Практическое
следствие: один зависший в вычислениях «тяжёлый» запрос больше не вешает
весь процесс, но всё ещё может голодать по CPU — справедливость на уровне
планировщика не равна гарантиям по latency.

## Ограничение конкурентности

«По горутине на задачу» не работает, когда задач миллионы (или когда за ними
ограниченный ресурс: БД, сторонний API). Два базовых приёма:

**Семафор на канале:**

```go
sem := make(chan struct{}, workers)
var wg sync.WaitGroup
for i := range items {
    wg.Add(1)
    sem <- struct{}{}          // занять слот (ждём, если все заняты)
    go func(i int) {
        defer wg.Done()
        defer func() { <-sem }() // освободить слот
        results[i] = validate(items[i])
    }(i)
}
wg.Wait()
```

**Worker pool:**

```go
jobs := make(chan int)
var wg sync.WaitGroup
for w := 0; w < workers; w++ {
    wg.Add(1)
    go func() {
        defer wg.Done()
        for i := range jobs {
            results[i] = validate(items[i])
        }
    }()
}
for i := range items {
    jobs <- i
}
close(jobs)
wg.Wait()
```

Обе схемы сохраняют **порядок результатов** одним приёмом: результаты пишутся
в `results[i]` по индексу — каждая горутина пишет только в свой элемент
слайса. Это безопасно без блокировок: гонка возникает при обращении к одной
ячейке памяти, а разные элементы слайса — разные ячейки (урок 7 — про
формальные гарантии).

`sync.WaitGroup` — счётчик ожидания: `Add(1)` перед стартом, `defer Done()`
в горутине, `Wait()` в конце. Правила: `Add` до запуска горутины (не внутри),
`Done` ровно один раз на каждую горутину.

## Утечки горутин

Горутина утекает, когда она **навсегда заблокирована** и никто её не ждёт:

```go
ch := make(chan int)
go func() {
    ch <- 1 // никто никогда не прочитает — горутина висит вечно
}()
```

Источники: отправка в канал без получателя, ожидание мьютекса, который никто
не освободит, HTTP-запрос без таймаута. Утечки не видны сразу: память
течёт медленно (2 КБ на горутину), но каждая утечка держит стек, и к
миллиону запросов вы «внезапно» упрётесь в OOM.

Обнаружение:

```go
fmt.Println(runtime.NumGoroutine()) // грубый счётчик
```

```sh
# точный список всех горутин со стеками — в pprof-профиле
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

В тестах счётчик горутин до/после ловит регрессии (см. практику урока 8),
в проде — pprof-профиль `goroutine` показывает, где они зависли и сколько их
(«все 40 тысяч ждут `send` на строке 42» — читается мгновенно). Библиотека
`goleak` автоматизирует такую проверку в тестах.

## Когда горутина не нужна

Горутина — средство, а не цель. Не нужна, если:

- работа быстрая и последовательная — вызов функции проще и быстрее
  (запуск горутины стоит ~десятки нс + аллокация, но главное — сложность);
- нужен **результат немедленно** — асинхронность ради асинхронности только
  добавляет синхронизацию;
- единственная цель — «запараллелить» 10 строк, читающих общий мьютекс, —
  получится сериализация с накладными расходами.

Признак здорового параллелизма: горутины общаются через каналы (следующий
урок) или защищённые структуры (урок 7), а не через общие переменные.

## Go vs Python: asyncio, GIL и потоки

```python
# asyncio: кооперативная многозадачность в ОДНОМ потоке
async def validate(item):
    await asyncio.sleep(0.001)   # await — точка передачи управления

results = await asyncio.gather(*(validate(it) for it in items))
```

```go
// Go: вытесняющие горутины на многих потоках
results := make([]Result, len(items))
var wg sync.WaitGroup
for i, it := range items {
    wg.Add(1)
    go func(i int, it Item) {
        defer wg.Done()
        results[i] = validate(it)
    }(i, it)
}
wg.Wait()
```

Принципиальные отличия:

1. **Где блокировка.** В asyncio блокирующий вызов (`time.sleep`,
   синхронный HTTP-клиент) замораживает **весь event loop** — кооперативная
   модель карает за каждую ошибку. В Go блокирующая горутина замораживает
   только себя: планировщик переключит M на другую.
2. **GIL.** CPython исполняет байткод строго в одном потоке за раз: потоки
   не дают CPU-параллелизма вообще (только I/O-перекрытие через тот же GIL
   release на блокирующих вызовах), параллелизм — процессы или asyncio.
   Горутины Go — настоящий параллелизм на ядрах.
3. **Точки переключения.** В Python — явные (`await`, I/O). В Go — неявные
   (планировщик + преемпшн): не нужно красить функции в async/def и
   переписывать стек под `await`.
4. **Структурированная отмена.** `asyncio.gather`/TaskGroup отменяет задачи
   при ошибке — в Go отмену несёт `context` (урок 8), группировку ошибок —
   `errgroup` (урок 7).

`ThreadPoolExecutor.map` — ближайший аналог worker pool из Go, но с ценой
потоков ОС и GIL на CPU-задачах. **C#:** `Task` + ThreadPool — семантически
ближе всего к Go (воркеры, work stealing в .NET ThreadPool тоже есть), но
`async/await`-машины состояний и `Task`-обёртки остаются явными, а в Go
синхронный на вид код уже асинхронный.

## Подводные камни и анти-паттерны

1. **Замыкание по переменной цикла.** До Go 1.22 `go func() { use(i) }()`
   захватывал переменную, а не значение, — все горутины видели последний `i`.
   С Go 1.22 переменные цикла переиспользуются по-новому, но привычка
   передавать значение явно (`go func(i int) { ... }(i)`) остаётся дешёвой
   страховкой.
2. **WaitGroup счётчик.** `Add` внутри горутины — гонка с `Wait`; `Done` без
   `Add` — паника `negative WaitGroup counter`. `defer wg.Done()` первой
   строкой горутины.
3. **GOMAXPROCS как «ускоритель».** Увеличение сверх числа ядер ускоряет
   только при блокирующих syscall-ах. Для CPU-нагрузки — хуже из-за
   переключений.
4. **Забытая синхронизация результата.** «Горутина пишет в слайс, main
   читает» без Wait — читатель может увидеть частичный результат или вовсе
   не увидеть (урок 7 — модель памяти).
5. **Утечки при ошибке.** Ранний `return` до `wg.Done()` / до чтения канала
   оставляет горутины висеть. При выходе по ошибке — отменяйте контекст и
   закрывайте каналы.
6. **Семафор без defer.** Забытый `<-sem` при ошибке — исчерпание пула и
   зависание следующих задач.
7. **Горутина на «тяжёлую» синхронную работу с общим мьютексом** — гонки
   хуже, чем последовательность.
