# Практика. Урок 5: параллельная валидация позиций

Пакет `validate`: конкурентная обработка слайса позиций с **сохранением
порядка результата** и **ограничением числа одновременно работающих горутин**.
Функция `validateItem` (проверка одной позиции) уже готова — вся работа в
`ValidateItems`.

## Задание

Реализуйте `TODO` в `validate/validate.go` (лекция: раздел «Ограничение
конкурентности»):

- результаты возвращаются в слайсе той же длины, что и вход, причём
  `results[i]` строго соответствует `items[i]` (`Index == i`);
- обработка параллельная, но число одновременно работающих горутин не
  превышает `workers` (если `workers < 1` — `runtime.GOMAXPROCS(0)`);
- каждая позиция валидируется ровно один раз;
- функция возвращается только после завершения **всех** горутин
  (`sync.WaitGroup`).

Подходы на выбор (оба из лекции):

1. **N исполнителей + канал заданий**: исполнители читают индексы из общего канала и
   пишут в `results[i]`; запись в разные элементы слайса из разных горутин
   безопасна без блокировок;
2. **семафор**: канал `struct{}` ёмкостью `workers` ограничивает число горутин,
   запускаемых на позицию.

Запускайте тесты с race detector — он и есть главный критерий этой практики:

```sh
go test -race ./...
```

## Критерий сдачи

```sh
go mod tidy
go vet ./...

```

Всё зелёное.

## Перенос в итоговый проект

валидации позиций, перенесённую из практики, но работающую через интерфейс
`domain.OrderValidator` (вместо локальной `validateItem`). Используйте её в
`OrderService.CreateOrder` вместо последовательного цикла валидации: при
ошибке хотя бы одной позиции заказ не создаётся (верните первую ошибку с
деталями, как в практике урока 3). Проверьте: `make test` (в итоговом проекте тесты
идут с `-race`) зелёный.
