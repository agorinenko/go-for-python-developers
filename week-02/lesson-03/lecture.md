# Урок 3. Интерфейсы и композиция

## Цели урока

- понять, чем implicit interface satisfaction отличается от «объявления» интерфейса
  и почему это меняет архитектуру кода;
- освоить малые интерфейсы на стороне потребителя и их роль в stdlib
  (`io.Reader`/`io.Writer`);
- закрепить nil-ловушку: интерфейс — это пара `(тип, значение)`;
- научиться композиции через embedding вместо наследования;
- спроектировать сервисный слой итогового проекта поверх интерфейсов.

## Задача из итогового проекта

На этом уроке заказ перестаёт быть «структурой с валидацией» и становится
системой: `domain.ListFilter`, `domain.OrderRepository`, `domain.OrderValidator`
(интерфейсы — контракт недели 2 в [CAPSTONE.md](../../CAPSTONE.md)) и
`service.OrderService`, который зависит только от них. Хранилища ещё нет — и
именно поэтому интерфейсы: сервис пишется и тестируется сейчас, PostgreSQL
подключится на неделе 6 без изменения сервисного слоя.

## Неявная реализация: нет «implements»

В Go связь типа с интерфейсом нигде не объявляется. Тип удовлетворяет
интерфейсу, если у него есть все методы с нужными сигнатурами:

```go
type OrderRepository interface {
    Save(ctx context.Context, o *Order) error
    GetByID(ctx context.Context, id string) (*Order, error)
}

// PostgresRepo ничего не знает про интерфейс OrderRepository.
type PostgresRepo struct { pool *pgxpool.Pool }

func (r *PostgresRepo) Save(ctx context.Context, o *Order) error { /* ... */ }
func (r *PostgresRepo) GetByID(ctx context.Context, id string) (*Order, error) { /* ... */ }

// и при этом его можно передать как OrderRepository
var repo OrderRepository = &PostgresRepo{}
```

Проверка соответствия — структурная, на уровне компилятора. Для
удобочитаемости (и чтобы ошибки находились в момент компиляции пакета, а не в
точке использования) принято добавлять assertion времени компиляции:

```go
var _ OrderRepository = (*PostgresRepo)(nil) // падает компиляция, если сигнатуры разошлись
```

Сравните с C#: `class PostgresRepo : IOrderRepository` — реализация декларируется
в типе, интерфейс «вытягивает» за собой зависимость от сборки, где он объявлен.
В Go зависимость направлена в другую сторону: интерфейс объявляется там, где
его **используют** (в `service`), а реализации о нём не знают.

## Малые интерфейсы и центр stdlib: io.Reader

Ядро стандартной библиотеки — два однострочных интерфейса:

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Один метод — и вся экосистема совместима: `os.File`, `net.Conn`,
`bytes.Buffer`, `http.Request.Body`, `gzip.Reader`, `crypto/tls.Conn` — всё
это Reader/Writer, а значит, работает со всеми функциями stdlib и всех
библиотек сразу. `io.Copy(dst, src)` перекачивает что угодно во что угодно:
сокет в файл, файл в gzip, HTTP-тело в буфер.

Это и есть принцип **«принимай интерфейсы, возвращай конкретные типы»**
(Postel'овское «be liberal in what you accept»): функция объявляет минимальный
контракт, который ей реально нужен, — и становится применимой к любому коду,
написанному до неё.

Большие интерфейсы — анти-паттерн: они прибивают потребителя к реализации
намертво, их невозможно подделать в тестах, и каждый лишний метод заставляет
ломать все реализации разом. Правило: **интерфейс из 3+ методов — повод
задуматься**, из 5+ — почти наверняка ошибка. Исключение осознанное: контракт
`OrderRepository` (4 метода) — граница хранилища, которую мы намеренно
замораживаем на курс; всё, что за ней, живёт в `internal/storage`.

## Интерфейс = пара (тип, значение), и nil-ловушка

Интерфейс в среде выполнения — два слова: указатель на **конкретный тип** и указатель
на **значение**:

```go
var repo OrderRepository          // (nil, nil) — интерфейс nil
repo = (*FakeRepo)(nil)           // (*FakeRepo, nil) — интерфейс НЕ nil!
fmt.Println(repo == nil)          // false
```

Классический сценарий катастрофы — функция возвращает интерфейс, внутри
которого nil-указатель:

```go
func NewRepo(cfg Config) (OrderRepository, error) {
    var r *PostgresRepo
    if cfg.DSN == "" {
        return r, nil // внутри интерфейса — (*PostgresRepo, nil)
    }
    return initRepo(cfg.DSN), nil
}

repo, err := NewRepo(cfg)
if err == nil && repo != nil { // repo != nil — проходим!
    repo.Save(ctx, o) // паника: разыменование nil-указателя
}
```

Лекарств два, и они не взаимоисключающие:

1. **Не возвращать интерфейсы из фабрик** без нужды — возвращать конкретный
   тип. Тогда nil-указатель виден честно: `var r *PostgresRepo; return r, nil`
   ловится вызывающим как `if r == nil`.
2. Внутри методов, возвращающих интерфейс, явно проверять конкретный тип:
   `if r == nil { return nil, errNoDSN }` — «nil возвращай как nil, а не как
   типизированный nil».

Та же пара `(тип, значение)` объясняет, почему интерфейс нельзя сравнивать с
`nil` внутри метода-приёмника, и почему `reflect`-сравнения интерфейсов
дороги. Про `any` — ниже.

## Композиция: embedding вместо наследования

Наследования нет. Есть **встраивание** — поле без имени: встроенный тип
«продвигает» (promotes) свои методы наружу:

```go
type countingWriter struct {
    io.Writer        // встроенный интерфейс
    n     int64
}

func (c *countingWriter) Write(p []byte) (int, error) {
    n, err := c.Writer.Write(p) // делегируем встроенному
    c.n += int64(n)
    return n, err
}

cw := &countingWriter{Writer: os.Stdout}
cw.Write([]byte("hi")) // метод продвинут из io.Writer; cw удовлетворяет io.Writer
```

`countingWriter` — не «наследник»: это структура, которая **содержит** Writer,
явно делегируя ему вызовы, — как композиция в классическом ООП, только с
синтаксическим сахаром. Никакого полиморфизма по иерархии: `countingWriter` и
`os.File` не имеют общего предка; они оба удовлетворяют `io.Writer`
независимо.

Интерфейсы тоже встраиваются — и это главный инструмент «малых интерфейсов»:

```go
type ReadWriter interface {
    Reader
    Writer
}
type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}
```

**C#-аналогия:** `class CountingWriter : Stream` — наследование реализации.
Go-аналог — `struct { io.Writer }` + делегирование. Для «разделяемого
поведения» в C# используют абстрактные базовые классы; в Go — либо встраивание
структуры с реализацией, либо просто функция (см. ниже про `Reusable`).
Embedding-интерфейсов в C# аналогичен `interface IReadWrite : IReader, IWriter`.

## Интерфейсы на стороне потребителя

`OrderRepository` объявлен в `domain`, но используется в `service` — это
«интерфейс потребителя»: контракт описывает **что нужно потребителю**, а не
что умеет реализация. Реализация (PostgreSQL на неделе 6, фейк в тестах)
просто обязана удовлетворить контракт.

Важно следствие для тестов: потребитель (OrderService) тестируется с фейком
в памяти — мгновенно и без базы. Реализация тестируется отдельно
(интеграционные тесты, неделя 6). Никто не тащит в тесты «настоящее»
хранилище.

И ещё следствие для архитектуры: не создавайте интерфейсы «на вырост» рядом с
реализацией («на всякий случай обернём репозиторий интерфейсом»). Интерфейс
появляется тогда, когда появляется **второй** потребитель или потребность в
подмене. До этого — конкретный тип.

## any вместо interface{}

`interface{}` с Go 1.18 называется `any` — это псевдоним. Изменилось не имя, а
роль: раньше `interface{}` был «дырой в типах», куда сваливали что попало;
теперь `any` — осознанный инструмент для ограниченного набора мест:

- `map[string]any` при разборе произвольного JSON (`json.Unmarshal` в карту);
- генерики там, где нужна **типобезопасная** обёртка, а не `any`;
- `fmt.Println(a ...any)` и подобные API.

Если вы пишете `any` в сигнатуре своего кода — спросите себя, не нужна ли
генерик-функция (`func Map[T, U any](s []T, f func(T) U) []U`) или конкретный
интерфейс. Дыра в типах заразна: она вынуждает вызывающих делать
type assertion — проверки, которые компилятор не видит:

```go
v, ok := x.(*Order) // ok — только если вы УВЕРЕНЫ в типе
```

`any` оправдан в библиотечном коде (сериализация, рефлексия), но в
бизнес-логике сервиса — сигнал плохого дизайна.

## Go vs Python: duck typing и структурная типизация

Python проверяет «утку» в среде выполнения, в момент вызова:

```python
# duck typing: ошибка всплывает при вызове, а не при передаче
def save(repo, order):
    repo.save(order)          # AttributeError, если у repo нет save

class FakeRepo:
    def save(self, order): ...   # никакого объявления соответствия
```

```go
// структурная типизация: несоответствие — ошибка компиляции
func save(repo OrderRepository, o *Order) error {
    return repo.Save(context.Background(), o) // компилятор уже проверил контракт
}
```

Python-мост к этому — `typing.Protocol` / `abc`:

```python
class Repo(Protocol):
    def save(self, order) -> None: ...

def save(repo: Repo, order): ...   # mypy проверит статически
```

Но различия принципиальные:

1. **Когда ловится ошибка.** Go — на компиляции, и не в точке использования,
   а сразу: `var _ OrderRepository = (*PostgresRepo)(nil)`. Python даже с
   mypy — это опциональный внешний инструмент; без него ошибка всплывает в
   проде (`AttributeError`).
2. **Стоимость диспетчеризации.** Вызов метода интерфейса в Go — косвенный
   вызов через itab (таблица методов), это наносекунды. Python ищет атрибут в
   словаре класса/объекта на каждом вызове.
3. **Пустой интерфейс.** `any` в Go ≈ `object` в C#, но в Python всё и так
   динамическое — понятие «дыры в типах» имеет смысл только в статическом
   контексте.

Итог: утку в Go заменяет не рефлексия, а компилятор. Вся «гибкость» duck
typing сохраняется (любой тип с нужными методами подходит), а её цена
(среда выполнения-сюрпризы) исчезает.

## Подводные камни и анти-паттерны

1. **Типизированный nil** (детально выше) — тестируйте ветки ошибок с
   nil-фабриками; правило: возвращайте конкретные типы, а в фабрике
   интерфейсов явно проверяйте `if concrete == nil`.
2. **Интерфейс рядом с реализацией.** `type Repo interface {...}` в одном
   пакете с `PostgresRepo` «для порядка» — мёртвый груз: подменять нечего,
   тестировать нечего, а контракт разъезжается. Интерфейс — у потребителя.
3. **Большой интерфейс.** 10 методов «всё-в-одном» невозможно ни подделать,
   ни заменить. Дробите: `Save`/`Get`/`List` — разные потребители, разные
   интерфейсы.
4. **Методы-указатели против методов-значений.** `func (r *PostgresRepo) Save(...)`
   — тогда интерфейс удовлетворяет только `*PostgresRepo`, а не `PostgresRepo`.
   Если метод меняет состояние (а Save меняет) — указатель обязателен; но
   тогда и хранить нужно указатель, а не значение.
5. **Сравнение интерфейсов.** `if err == myErr` работает только пока ошибки
   не оборачиваются — только `errors.Is` (урок 2). Сравнивать интерфейсы `==`
   можно, только если и тип, и значение comparable, — иначе паника в среде выполнения.
6. **`any` в бизнес-логике** — дыра в типах; проверки типа (`x.(*Order)`)
   размазываются по коду и молча ломаются при рефакторинге.
7. **Множественное встраивание с коллизиями.** Два встроенных типа с
   одинаковыми методами — неоднозначность, которую компилятор заставит
   разруливать явно. Коллизии полей (в т.ч. с «тенью» от вложенных структур) —
   источник тонких багов; встраивайте осознанно, не ради экономии строк.
