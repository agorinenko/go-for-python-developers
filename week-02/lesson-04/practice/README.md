# Практика. Урок 4: тестирование как в промышленности

Эта практика — «наоборот»: пакет `discount` (расчёт скидок) дан **целиком
рабочим**, без единого TODO. Ваша работа — тесты. Они и есть критерий сдачи:
как в реальном проекте, где тесты защищают чужой (или свой вчерашний) код.

Код `discount/discount.go` — эталон поведения, его менять нельзя.

## Задание

Создайте `discount/discount_test.go` и покройте пакет тестами:

1. **Table-driven** на чистых функциях (лекция, раздел «Table-driven тесты»):
   - `CategoryTotal`: попадание категории, несколько позиций, пустой вход,
     категория без позиций;
   - `DiscountFor`: порог (subtotal == Threshold, на копейку меньше, на копейку
     больше), `Percent` на границах и за границами (0, 100, -5, 150),
     subtotal 0 и отрицательный;
   - `ApplyRules`: одно правило, выбор правила с наибольшим порогом,
     tie-break по проценту, правила другой категории не влияют, нет правил → 0.
2. **testify** (`assert`/`require`): используйте в тестах `MakeBill` и
   `FormatBill`; `require` — там, где дальнейшие проверки не имеют смысла без
   условия (например, `require.Equal` количества позиций перед проверкой полей).
3. **Golden file**: тест на `FormatBill` с эталоном в
   `discount/testdata/TestFormatBill.golden` и флагом `-update`:
   `flag.Bool("update", false, ...)`; если флаг поднят — перезаписать файл,
   иначе — сравнить с содержимым файла (лекция, раздел «Golden files»).
4. **Граничные случаи**: `FormatKopecks` (0, 5 копеек, ровно рубль, минус),
   пустой заказ, скидка 100% (Total == 0).
5. **AAA-структура** в каждом тесте: Arrange / Act / Assert с комментариями
   (тесты — документация, их читают на ревью).

Сгенерируйте golden-файл один раз через `go test -run TestFormatBill -update`
(флаг объявляется после имени пакета — так `go test` передаст его тестовому
бинару), проверьте его содержимое глазами (это ВАШ эталон) и закоммитьте.
Ветку `-update` не забудьте про `os.MkdirAll("testdata", 0o755)` перед
`os.WriteFile` — WriteFile не создаёт родительские каталоги.

## Критерий сдачи

```sh
go mod tidy   # до написания тестов tidy УДАЛИТ require testify из go.mod
              # (код его ещё не импортирует) — это нормально; после того как
              # тесты импортируют testify, tidy вернёт зависимость и go.sum
go vet ./...
go test -race ./...
go test -cover ./...   # покрытие пакета discount ≥ 90%
```

Все команды зелёные; итоговое покрытие — не ниже 90% (без погони за процентами
ради процентов: каждая строка покрытия должна соответствовать осмысленному
кейсу).

## Перенос в капстоун

Тесты `OrderService` (урок 3) сейчас используют только stdlib. Перенесите в
капстоун практики этого урока:

1. Подключите `github.com/stretchr/testify` в модуль `orders`.
2. Перепишите юнит-тесты `orders/internal/service` в стиле практики:
   table-driven, AAA-комментарии, testify `assert`/`require`,
   `require.ErrorIs` для проверок `errors.Is`.
3. Доведите покрытие `internal/service` до ≥ 90%: добавьте недостающие кейсы
   (пустой customer, пустые items, лимит в `ListOrders`, повторная отмена).
4. Golden-файлы сервису не нужны (отчёт — текстовый артефакт, в сервисе его
   нет), но примените приём там, где появится форматированный вывод
   (неделя 5, JSON-контракты — `testdata/*.json`).
